# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Git: never commit without an explicit go-ahead

**Never run `git commit` (or amend, cherry-pick or anything else that creates a commit) unless the user has clearly said to commit, in that same request.** Finishing a task, passing checks, a clean working tree or an earlier "commit" does **not** count as permission. Each commit needs a fresh, explicit go-ahead; one approval does not carry over to later work. Do the work, leave the changes uncommitted, say what changed, and wait to be told to commit. Pushing is a separate step that also needs an explicit request.

When you are told to commit, split unrelated work into separate commits.

Maalu is a personal finance tracker. It is a monorepo: `apps/api` (FastAPI, async SQLAlchemy 2.0, Alembic, Python 3.13, uv workspace) and `apps/web` (TanStack Start, React 19, MUI v9, Zod, pnpm workspace `@maalu/web`). Both are driven from the root `justfile`.

## API architecture (`apps/api/app`)

The layers go `models` → `schemas` (Pydantic) → `services` → `routers`, connected in `dependencies.py`:
- Each service is a class built from an `AsyncSession` and injected through `*ServiceDep` aliases. Routers take `CurrentUserId` and pass `user_id` into every service call. **Every query is scoped to the user**, and a row belonging to another user returns 404, never 403.
- Services raise domain exceptions (exported from `app/services/__init__.py`, for example `VendorNameTakenError` and `TransactionRuleError`). Routers turn them into `HTTPException`s (409 or 422). Services never import FastAPI.
- `get_db` commits when the route returns, **before** the response is sent (`DbSession` is `Depends(get_db, scope="function")`). The default scope would commit after the response, so the web app's refetch after a mutation could read the old data and a failed commit would never reach the client. A test pins the scope. An explicit `commit()` inside a service (as `check_second_factor` does before it raises) is for state that must survive a failing request.
- List endpoints return plain JSON arrays. `limit` is optional (leave it out to get all rows, which dropdowns use), and the total count goes in the `X-Total-Count` header via `app/pagination.py` (`PageDep`, `set_total`). Services provide a `list_for_user` / `count_for_user` pair built on a shared `_conditions()` filter builder.
- Text search uses `icontains(..., autoescape=True)`.

Money domain rules:
- Money is `Numeric(19, 4)` and `Decimal` from end to end, serialised as **strings** in JSON. Never use float.
- A transaction's `amount` is always positive, and `type` (income/expense/transfer) sets the direction. `exchange_rate` is in base-currency units per 1 unit of `currency`, and `base_amount = amount * exchange_rate`, rounded half-even to 4dp (`services/money.py`). The rate is forced to 1 when the currency matches the user's `base_currency`; otherwise the client must supply a rate.
- For a transfer, `account` is the source and `amount` is what left it; `to_account` and `to_amount` (in the destination's currency) are what arrived.
- Categories are a table (unique per user ignoring case). Requests send the category *name* and the API finds-or-creates it, like vendors; responses carry `category` (name) and `category_id`. Transactions, split lines and subscriptions all point at it, and transfers have none. A category in use can't be deleted, only merged into another (`POST /categories/{id}/merge`).
- A transaction can be split into items (`transaction_splits`: name, quantity, category, tax-inclusive `amount`, optional `tax_amount`) that must add up exactly to its `amount`; its own category is then the biggest item's. Category reporting (`/transactions/categories`, the export's By category sheet) shares a split's `base_amount` across its items with `app/allocation.py`, so totals agree exactly. Filtering by category lists every transaction touching it but counts only the matching items' share in totals.
- The budget is simple limits, not envelopes: a line is a per-period amount for some categories (each category in one line at most). **A limit can also be for set dates** (`budget_lines.ends_on`, with `start_date` as its first day; `start_date` + `end_date` on create and update, both or neither, end not before start, at most ten years, no rollover): its `amount` is then **one total for the whole stretch**, counted once over `start_date`..`ends_on` (`BudgetService._fixed_view`, the same activity rules as any line), not per period. **Fixed limits are separate from the per-period lines**: they are returned in `fixed_lines` (every one, whatever period is shown, each with `state` upcoming / active / ended and `days_left`; running ones first, ended last), they are **not in `lines` or `totals`**, and `attention` counts a running one that is close or over. The "each category in one line" rule only applies **within a kind**: two per-period lines can't share a category, two limits for set dates can't share one when their dates overlap (`_overlap`; the ends count), but a fixed limit and a per-period one may. A PATCH can give a per-period limit both dates (it becomes a fixed one, rollover off), change one end of a fixed one, or send `end_date: null` to make it per period again (`start_date` is then reset to the current period; a lone date on a per-period limit is a 422). Notifications and the save-time warning treat a **running** fixed limit like a line of the current period (`budget:<line id>:<start_date>:<status>`; the web warning only fires when the expense's date is inside the dates, even when another period is on screen: `budgetWarning(budget, categories, on)`). Web: the limit form's "Only for certain dates" switch (From and Until, the amount relabelled "Limit for these dates", rollover hidden, categories taken by an overlapping limit disabled), a "For set dates" section on the Budget page under the per-period cards (each card shows its dates and days left), not in the summary above it. **The API returns every one, but the page lists only those whose dates touch the period on screen** (`fixedInPeriod` in `lib/budget.ts`), so a November limit is not shown under December; the form still reads the full list to tell which categories are taken. **A monthly limit can run only between two dates** (`budget_lines.active_until`, `BudgetLineCreate.repeat`, `BudgetLineUpdate.repeat`): with both dates and `repeat: true` the limit stays per-period (`ends_on` null, `amount` is per period, rollover allowed) but only exists in the periods the dates touch; **the dates snap to whole periods** (`start_date` = first day of the period holding the start, `active_until` = last day of the one holding the end) and the response says so (`runs_from`, `runs_until`, null for one that runs for ever). `view()` leaves it out of `lines`, `totals`, `attention` and the notifications outside its periods (`_runs_in`). Overlap is by kind and days (`_span_of`, `_overlap`): a fixed limit only meets fixed ones, a monthly one meets monthly ones in any period both run in (so Nov to Jan and Feb to Apr may share a category, a monthly one that runs for ever clashes with both); the web form leaves that check to the server for these. A PATCH with the dates keeps the limit's kind unless `repeat` says otherwise (true: monthly between dates, false: one total; moves of a limit that stops being monthly go, as before); `end_date: null` makes it run for every period again (start reset to the current period). **A move needs both limits to run in the period it is for** (422 otherwise). Web: the form's "How it counts" select under the dates, "Runs …" on the card. **Rolling a finished (or running) fixed limit over** is web only: "Repeat for the next stretch" on its card opens `BudgetLineForm` as a new limit (`repeatOf`) filled in with the same name, categories and amount, starting the day after and as long (`nextStretch`), and saves through the normal create. **The page lists a fixed limit only under the period its dates touch** (`fixedInPeriod`), and **the dashboard's Budget and goals card lists the running ones** with a meter (`runningFixed`), even when there are no per-period limits. Not built: a fixed limit's own history across stretches. Periods are months starting on `period_start_day` (default 1), derived in `app/budget_period.py`, never stored. Activity is expenses in `base_amount` (split items under their own categories); status is `ok` / `warning` (at or above the warning percent, default 80, per line or per budget) / `over`. Rollover carries unspent money only, looking back at most 24 periods from the line's `start_date`. **Moving money between limits** (`models/budget.py: BudgetMove`, table `budget_moves`; `POST /budget/moves {to_line_id, from_line_id?, amount, on?, note?}` and `POST /budget/moves/{id}/undo`, both answering with the budget for that period; `GET /budget/lines/{id}/moves` is the limit's **history**): money moved from one monthly limit to another for **one period only**, or added to one (no `from_line_id`, a top-up, which raises `totals.amount`; a move between limits leaves it as is). A line's `amount` stays its usual amount; `moved_in` and `moved_out` are this period's, and `available`, `percent`, `status`, the totals and rollover (each earlier period's moves, through `net` in `view`) all use amount + carried + moved_in - moved_out. **A source gives at most what it has left that period** (422 "has only MVR X left" / "has nothing left"); a top-up has no cap. Only monthly limits take part: a limit for set dates is refused (422), and giving a monthly limit dates deletes its moves; deleting a limit deletes them too (`ON DELETE CASCADE`). A move stores its period's first day and is matched to periods **by date range**, so changing `period_start_day` later still finds it. `BudgetResponse.moves` lists the period's moves, newest first. **Undo never deletes**: it sets `undone_at`, the budget ignores undone moves (`_moves`), and the history keeps them, so it is a log of what moved where (a second undo is 404). The history (`BudgetMoveLogEntry`: the move plus its `period_start`, `period_end` under the current start day, and `undone_at`) lists every move into or out of the limit, in every period, newest first. Moves are in backups (an owned table). Web: `MoveMoneyDialog` ("Move money here" on each monthly card; From lists the other limits with what they have left, most first, an empty one disabled, plus "Nowhere: just add to this limit"; `moveProblem` checks the cap in the browser too), each card lists its moves (`movesFor`: "+MVR 600.00 from Dining this period", "−MVR 600.00 to Groceries", "+MVR 300.00 added") with Undo, a **History** button opens `MoveHistoryDialog` (grouped by period with `historyByPeriod`, each move with its note, when it was made and, struck through with an Undone chip, when it was undone), and `periodLimit` is the card's "of" figure (`lib/budget-moves.ts`).
- Goals (`/goals`) are savings targets in the base currency. A goal either follows one savings account's balance (one goal per account; cards and loans refused) or, with no account, a log of amounts set aside by hand (`goal_entries`, signed). An optional monthly plan reports what was set aside in a budget period: for an account goal, transfers into the account less transfers out (income and interest are not contributions). `needed_per_month` is the remaining amount over the whole months left, rounded up.
- FKs to vendor/subscription/account use `ON DELETE SET NULL`, so deleting them unlinks transactions and keeps them. User FKs cascade.
- **Deleting a transaction moves it to the trash** (`deleted_at`): `DELETE /transactions/{id}` sets it, `GET /transactions/trash` lists, `POST .../restore` brings it back, `DELETE .../permanent` removes it for good (only from the trash). The one exception to "trashed rows are invisible" is the category in-use check, which counts trashed rows because their `category_id` FK has no `ON DELETE`.
- **Time of day:** a transaction has `transaction_date` plus an optional `transaction_time` (a `Time` column, the clock as read on the wall, no time zone; `null` means unknown, and `PATCH` with `null` clears it). It only orders one day: lists sort by date, then time (newest first, soonest first for upcoming), with untimed ones after timed ones (`nulls_last()`), then by `created_at`. Filters stay on the date. The export has a Time column after Date. Templates, duplicates and "Add another" do not carry a time (the date resets, so the time would be stale). The web form has a Time field next to Date, and the lists show it after the date (`formatWhen` / `formatTime` in `lib/format.ts`).
- **Planned transactions** (`planned`): something coming up that has not happened yet (rent due next month). `Transaction.live()` means not trashed and `Transaction.counted()` means not trashed and not planned. **Anything that sums money (balances, budgets, goals, totals, category totals, monthly stats, the balance trend, a subscription's last payment, the export) must use `counted()`, and anything that sums income or spending across accounts (totals, category totals, the budget, monthly stats) must use `Transaction.reported()`, which also drops balance adjustments and excluded accounts**, and `live()` is for anything that only needs the row (get, bulk, tags usage); `_conditions()` does it for the list, count, totals and export. The list shows posted transactions by default and `?planned=true` shows the planned ones instead, soonest first (so totals always match the list). `POST /transactions/{id}/post` (optional `{transaction_date, transaction_time, amount}`; an explicit `null` time clears the planned one) turns a planned one into a real one (409 if it is not planned); a plain `PATCH` with `planned` flips it either way. A planned transaction whose date has passed just stays planned: the web shows it as overdue, the API has no such state.
- **Refunds** give money back for an earlier purchase. A refund is an **income** transaction with `refund_of_id` pointing at a posted, live **expense** (and, for a purchase with items, lines with `refund_of_split_id` naming the items given back); no new type. It is **money back for spending, not income**: wherever spending is summed, a refund takes away instead of adds. `Transaction.is_refund()`, `Transaction.spending()` (expenses and refunds), `Transaction.spending_base()` (signed SQL) and `spending_sign` (for the Python allocation loops) are what to use, in the same places `counted()` is: list totals (`income` leaves refunds out, `expense` is net, `refunded` says how much), category totals (a refund counts under its category's `expense`, negative), budget activity, monthly stats (counted in the month the refund arrives, so a month can go below zero), the export (Type "Refund") and the dashboard. Account balances still receive it (it is income to the account). A refund has the purchase's **currency** (and, unless typed, its rate), its **category** (forced; a purchase with items is refunded item by item, each line taking the item's name and category), and gives back **at most what is left** of the purchase (or of each item); refunds can be partial and repeated, planned ones reserve their share. The purchase side: `refunded_amount` (live refunds, in its currency) is a `column_property` on `Transaction` and on `TransactionSplit`; `refund_of` loads with `lazy="joined", join_depth=1` (`selectin` and `immediate` did not load it). A purchase **with live refunds keeps its amount, currency, category, items, type and posted state** (sending the same values back is fine, and unchanged items are kept so the links hold) and **cannot be trashed** until its refunds are (a bulk trash takes both together); **restoring a refund** needs its purchase live and room left (bulk restore does purchases first). A refund's type and category are fixed, it cannot move to another purchase, and `PATCH {refund_of_id: null}` turns it into plain income. **The other way round, existing income can be linked to a purchase** with `PATCH {refund_of_id: <purchase id>}` (`TransactionService._link_refund`, then the usual `_check_refund` at the end of `update`): only plain income (not an expense, transfer, adjustment, itself or something already a refund); the purchase must pass `_refund_original` (yours, posted, live, an expense); it keeps its own date, amount, account, rate, payment method and notes, takes the purchase's category (a different one is a 422), replaces its own items, and must be in the purchase's currency and within what is left; **a purchase with items needs `splits` naming the items** (each with `refund_of_split_id`, adding up to the amount). It then counts as spending given back instead of income everywhere refunds do. `GET /transactions/{id}/refund-candidates?q=&limit=` lists the purchases it could be for (same currency, on or before its date, with at least its amount left; the same amount first, then the same vendor, then the most recent; 422 for anything but plain income). Web: income rows have a link button ("Link to a purchase", `canLinkRefund`; it shares `refundOf` with the expense row's Refund button, `useRefundDialog` picking `{income}` or `{purchase}`) that opens `LinkRefundDialog`: a search over the candidates, and for a purchase with items the same item picker as a refund, which must add up to the deposit. Deleting a purchase for good unlinks its refunds. Bulk category changes skip refunds and refunded purchases. `app/seed.py` makes a few.
- **Accounts are archived, not only deleted** (`archived_at`): `POST /accounts/{id}/archive` and `/unarchive`. An archived account leaves the default list (`?archived=true` lists them), the summary, the balance trend, and the account pickers; its transactions stay and still count in category, budget and monthly stats. New transactions and new goal links to it are refused (422), but a transaction already in it can still be edited (the web form keeps its account in the picker). `get` returns archived accounts too.
- **Templates** (`/templates`, table `transaction_templates`) are saved starting points: type, optional amount, currency, payment method, category, vendor, account (and `to_account` for a transfer), description. Category and vendor go in and out by *name* (found or created, like transactions), the exchange rate is deliberately not stored (the form suggests the market rate for the day), and every link is `ON DELETE SET NULL`, so a template never blocks deleting an account, vendor or category. A template with an account takes that account's currency; an archived account is refused. `PATCH` only renames; to change what a template fills in, delete it and save it again.
- **Category colours and parents:** a category has a `color` (one of `ACCENT_COLORS` in `app/enums.py`, the same eight names as tags; a new one gets the least used automatically, or the one sent) and an optional `parent_id` (one level only: a parent cannot have a parent, a category with sub-categories cannot get one; `CategoryParentError` is a 422). A parent **includes its children**: filtering transactions by it, category totals, the export, and a budget line on it all use the family (`CategoryService.family`), and a budget line conflicts with a line on its parent or child. The parent is still usable on a transaction directly. The list is ordered parent then children; deleting a parent unlinks its children (`ON DELETE SET NULL`), and merging moves sub-categories. Responses carry `color`, `parent_id`, `parent`, `child_count`; transactions and split items carry `category_color`; `CategoryTotal` has `color`, `parent_id`, `parent`, `parent_color`.
- **Tags** (`/tags`, tables `tags`, `transaction_tags`, `template_tags`) are labels that cut across categories. A tag is unique per user by normalised name, has an automatic colour (one of `TAG_COLORS` in `models/tag.py`, the least used one first, named after the web accents), and belongs to the whole transaction, never to a split item. Requests send tag *names* (`tags: [...]`, at most 10) and the API finds-or-creates them, like categories; on update, `tags` replaces the list and `[]` or `null` clears it. Deleting a tag only unlinks it (it never blocks, unlike a category); `POST /tags/{id}/merge` moves everything to another tag without duplicates. Transactions, templates, the tag filter, the `q` search and the export's Tags column all know about them. The filter takes `tag_id` repeated plus `tag_match` (`any`, the default, or `all`), and a transaction with several of the chosen tags still counts once; a tag's `transaction_count` leaves out trashed transactions.
- **Bulk actions** work on up to 500 transaction ids per request and report instead of failing: every endpoint returns `{updated, skipped: [{id, reason}]}`, and an id that is not yours, not found or in the wrong state (live vs trashed) is just listed as skipped. `POST /transactions/bulk/trash`, `/bulk/restore` and `/bulk/purge` (purge only takes ones already in the trash) and `PATCH /transactions/bulk` (set `category`, `vendor_name` and `payment_method`, `add_tags`, `remove_tags`; at least one). A field that does not fit a transaction is left alone: transfers take only tags, and a split transaction keeps its items' categories. To act on everything a filter matches (all pages), `GET /transactions/ids` takes the same filters as the list and returns the matching ids (`?planned=true` for upcoming), and `GET /transactions/trash/ids` the trash's; both refuse with 422 past `MAX_SELECT_ALL` (5,000) rather than return a part. The bulk routes, `/ids` and `/trash/ids` are declared before `/{transaction_id}` so they aren't parsed as an id.
- **Vendor merge** (`POST /vendors/{id}/merge` with `{into_id}`) moves every transaction (trashed ones too), subscription and template to the target, copies what the target lacks (address, contact, currency, local or foreign, usual category, usual tags; what it has is kept), then deletes the source. Deleting a vendor, unlike merging, just unlinks its transactions.
- **Vendor defaults:** a vendor can carry a `default_category` and `default_tags` (by name in requests, found or created; `default_category: null` or `default_tags: []` clears them; deleting the category or a tag only clears the default, and merging a category or tag moves them). They are a convenience for the web form and the API never applies them itself: a transaction always says what it is.
- **Default account:** `users.default_account_id` (`PATCH /users/me` with `{default_account_id}`, `null` clears it; the account must be yours and not archived). It is cleared when the account is archived and unlinked when it is deleted. The API never applies it: the web form starts a brand-new transaction in it, with the account's currency and suggested payment method. The cookie session only caches id, email and base currency, so pages that need the default read `/users/me` in their loader.
- **Registration is controlled by `REGISTRATION`** (`Settings.registration`, `UserService.registration_open`): `auto` (default) lets an account be created only while none exists, so the first person to open a new instance is its owner and sign-up then closes; `open` lets anyone; `closed` lets no one (accounts come from `just seed` or the database). `POST /auth/register` answers 403 "Registration is closed" and `GET /auth/registration` (`{open}`, no login) is what the web login page (hides "Create one") and register page (shows a closed notice) read. Existing accounts sign in as usual. Maalu is self-hosted only, so the default is closed-after-owner. A way for the owner to add a partner is planned, not built. Tests default to `open` in `conftest.py`; `test_registration.py` covers the modes.
- **Passwords.** `POST /auth/password {current_password, new_password, code?}` (`UserService.change_password`) needs the current password and, when two-factor is on, a code or recovery code (a stolen session plus a known password must not be able to lock the owner out). New passwords follow the sign-up rules (8 to 128 characters) and must differ from the current one. It keeps this session and **ends the others**. A wrong current password is **422, never 401**, and counts toward the **sign-in rate limit** for that account (`rate_limit.login_failed`), so a stolen session cannot be used to guess the password; the password is checked before the code. Someone who forgot theirs is recovered by the operator, with no email: `just reset-password EMAIL` (`python -m app.admin reset-password EMAIL`, in Docker `docker compose -f docker-compose.prod.yml exec -it api python -m app.admin reset-password EMAIL`) asks for the new password twice, hidden, sets it (`UserService.set_password`), signs the account out everywhere (`SessionService.end_all`) and leaves two-factor as it is. Tests reach the database through `client.session_factory`.
- **Sessions are rows, and ending one deletes the row** (`models/session.py`, `services/session.py`, table `sessions`). Signing in makes a random 256-bit token (`security.new_session_token`); only its SHA-256 hash is stored, so a copy of the database holds nothing that signs in. The token is the bearer token (there is no access JWT any more; the only JWT left is the five-minute two-factor challenge). `get_current_user` / `CurrentSession` (`dependencies.py`) look the token up on every request, which is one small query. A session lasts `session_days` (30, `SESSION_DAYS`) **after its last use**: using it pushes the end out again, at most once an hour (`TOUCH_EVERY`), so a device you use now and then stays signed in and a lost one expires. A user switched off (`is_active`) fails the lookup. Expired rows are removed at the user's next sign-in. Each session records the browser (`User-Agent`, 255 characters) and the address it signed in from, only to tell your devices apart. Routes: `POST /auth/logout` (ends this session at once), `GET /auth/sessions` (yours, most recently used first, `current` marks the asker), `DELETE /auth/sessions/{id}` (404 for someone else's), `POST /auth/sessions/end-others` (declared before the `{id}` route). **Turning two-factor on or off, or making new recovery codes, ends your other sessions** (they were made without the second factor); a failed attempt ends nothing. Tests move time through `services.session._now`.
- **Rate limiting** (`app/rate_limit.py`, `Settings.rate_limit` / `RATE_LIMIT`, on by default) slows down guessing, in memory: a sliding window per key, nothing to install, a restart forgets it (it assumes one API process, the default; with several workers each counts on its own). Failed password attempts count per **account** (the email trimmed and lower-cased, whether or not it exists, so the answer never shows which emails are registered) and per **client address**: ten wrong passwords for one email, or thirty from one address, in fifteen minutes answer **429** with `Retry-After` and "Too many attempts. Try again in N minutes" (a `RateLimitedError` turned into the response by a handler in `main.py`, so services stay free of FastAPI). A right password clears that account's count. Wrong 2FA codes also count per address (twenty), on top of the per-user lock; sign-up attempts per address (ten an hour). **The browser never talks to the API, so the API only sees the web server**: `apiRequest` passes the visitor's address in `X-Forwarded-For` and uvicorn replaces `request.client` with it only for hosts in `FORWARDED_ALLOW_IPS`, which `docker-compose.prod.yml` sets to `*` because the API has no published port. Without that every visitor would share one limit. Behind a reverse proxy the web server needs the proxy to set `X-Forwarded-For`; if the web port is exposed directly a client can forge it, which only defeats the per-address limit, not the per-account one. A locked account locks the owner out of signing in for the rest of the window too (the price of a per-account limit). Tests turn it off (`RATE_LIMIT=false` in `conftest.py`) and `test_rate_limit.py` turns it on with a fake clock.
- **Two-factor sign-in** (authenticator-app codes, TOTP) is built in the API, not with a library service: `app/two_factor.py` (pure helpers: pyotp codes, Fernet encryption of the secret with a key derived from `SECRET_KEY`, recovery codes, the QR as an SVG data URI), `UserService` (state and rules), `routers/auth.py`. Columns on `users` (`two_factor_secret` encrypted, `two_factor_enabled`, `two_factor_last_step`, `two_factor_failures`, `two_factor_locked_until`) and a `recovery_codes` table (only SHA-256 hashes; `used_at`). Setup is `POST /auth/2fa/setup` (a secret, nothing changes yet; asking again before it is confirmed returns the **same** secret, so a repeated or racing request can never leave the screen and the server holding different ones) then `/auth/2fa/enable {code}`, which turns it on and returns ten recovery codes **once**; `/auth/2fa/disable` and `/auth/2fa/recovery-codes` need the password **and** a code. Sign-in becomes two steps: `POST /auth/login` returns `{two_factor_required, challenge_token}` and no `access_token` (a challenge is a five-minute JWT with a `scope` claim that `decode_access_token` refuses); `POST /auth/login/2fa {challenge_token, code}` gives the token. A code is accepted a step either side of now, **once** (`two_factor_last_step`); a recovery code works once; five wrong codes in a row lock the second factor for five minutes (`check_second_factor` commits the count before raising, since the failing request would roll it back). A wrong password or code on a signed-in route is **422, never 401**: the web app takes a 401 to mean the session ended. Changing `SECRET_KEY` makes stored secrets unreadable, so two-factor has to be set up again (it already signs everyone out). Someone who lost both the app and the codes is recovered by the operator: `just disable-2fa EMAIL` (`python -m app.admin disable-2fa EMAIL`, in Docker `docker compose -f docker-compose.prod.yml exec api python -m app.admin disable-2fa EMAIL`). Tests freeze the clock through `two_factor._now`.
- **Balance snapshots** (`models/balance_snapshot.py`, `services/snapshot.py`) are what each account held and was worth at the end of each **completed day** (`balance`, `exchange_rate`, `base_value`, one row per account per day; today is never stored, it is worked out live). `GET /stats/balance-trend` reads them for past days and computes only today and later from transactions (`StatsService._snapshot_points` / `_live_points`), so the chart no longer replays history and **revaluing an account never rewrites the past** (each day keeps the rate it had). Balances stay derived from transactions and are the source of truth, so snapshots are **repaired when an older transaction changes**: an `after_flush` listener on every `Session` (`mark_stale_snapshots`) writes a row in `balance_snapshot_dirty` (account, earliest affected day; upserted, keeping the earliest) for any added, changed, trashed or deleted transaction dated before today, for an account that is new (marked from 1900 to build its history), or whose opening amount changed. Today and later are never marked. `SnapshotService.repair(user_id=None)` first rebuilds each marked account from its mark (`rebuild`: replaces the rows from that day, keeping the rate of any day that already had one), then adds the days since each account's last snapshot; the trend calls it for the user before reading, and the daily `snapshot_balances` job (00:10 UTC) calls it for everyone, so the chart is right even with no worker running and the job mainly keeps the day's rate honest. A day before an account's first snapshot counts its opening amount at the current rate; archived accounts keep their snapshots but stay out of the trend. Days go by UTC (`snapshot._today()`, which tests replace with a fake clock; `stats.py` reads it as `snapshots._today()` so the patch reaches it). The migration marks every existing account stale, so history is built on first read. If the exchange rate is edited before the job has snapshotted yesterday, yesterday takes the new rate (a known one-day edge).
- **Background jobs** run in a separate worker process with procrastinate (`app/jobs.py`; the queue is Postgres tables, so nothing else to install): `just dev-worker` locally, the `worker` service in `docker-compose.prod.yml` (the API image with the command `procrastinate --app=app.jobs.app worker`; run one) in production. The API never runs a job. A job is an `@app.task` function that opens its own `SessionLocal` session (there is no request); `@app.periodic(cron=...)` above it schedules it, and procrastinate defers a periodic job once however many workers run. Jobs so far: `purge_expired_sessions`, daily at 03:17 (`SessionService.purge_expired`), `snapshot_balances`, daily at 00:10 (see Balance snapshots), `plan_subscriptions`, daily at 00:20 (see Subscriptions plan their next payment), and `purge_orphan_attachments`, daily at 04:30 (see Attachments), `generate_notifications`, daily at 04:00 (see Notifications), and `refresh_exchange_rates`, daily at 16:30 (see Rate refresh). The queue's schema is an Alembic revision (`b4e8d1a7c3f2`) that runs a **frozen copy** of procrastinate's SQL (`migrations/sql/procrastinate_3_10_schema.sql`) through asyncpg's simple-query `execute` (asyncpg refuses several statements in one prepared statement), and `include_object` in `migrations/env.py` keeps `procrastinate_*` tables out of autogenerate. **When procrastinate is upgraded, add a revision that runs its new files from `procrastinate/sql/migrations/`**, do not edit the frozen one. The worker needs `PYTHONPATH` to include `apps/api` (the compose service and `just dev-worker` set it). Tests call the job's plain function with `client.session_factory` and use procrastinate's `InMemoryConnector` to check a task can be deferred; they never need a worker or Postgres.
- **Backup and restore** (`services/backup.py`, `routers/backup.py`, Settings > Backup) is one JSON file of everything the user owns. `GET /backup` downloads it; `POST /backup/restore` takes the file as the request body (not multipart; capped at 200MB, held in memory). It is **metadata-driven**: `OWNED` (tables with `user_id`) and `CHILDREN` (tables tied to an owned row through one column) name the tables, and rows are read and written straight from the database tables, so a new column is backed up automatically. **A test fails when a new table is in neither `OWNED`/`CHILDREN` nor `EXCLUDED`**, forcing a decision (excluded: users, sessions, recovery codes, the exchange-rate cache, balance snapshots, which are rebuilt, and attachments, whose files live in storage). The file has `format`, `version`, `settings` (base currency, start-from-template, default account), `counts`, a SHA-256 `checksum` of the tables and the `tables`. **A restore goes only into an empty account** (409 otherwise; "empty" means no row in any included table, **except the budget row itself**: it is only settings, made by looking at the budget page (so every new account has one after its first visit to the dashboard), and a restore deletes it and puts the backup's own in; a budget with limits is not empty because `budget_lines` is counted), gives **every row a new id** (so the same file can go into two accounts, or back into the instance it came from, without colliding; foreign keys are rewritten through id maps, and columns that point into the same table, like `refund_of_id` and `parent_id`, are filled after the rows exist), sets the user's base currency and settings from the file, and marks every restored account stale so its snapshots are rebuilt on first read. Tables go in dependency order (`sort_tables`) in chunks of 1000. Any problem (not our format, other version, bad checksum, unknown table or column, a link to a row that is not in the file, a database error) is a 422 and **nothing is restored**, because the request's transaction rolls back. The backup holds no password, session or two-factor secret but is the user's financial data in plain text. The web side forwards both through `routes/api.backup.ts` (the browser cannot reach the API) and, after a restore, re-reads `/users/me` to refresh the base currency the session cookie caches; `BackupCard` is the Settings card.
- **Attachments** (receipts: JPEG, PNG, WebP or PDF) on a transaction (`models/attachment.py`, `services/attachment.py`, `routers/attachment.py`, `app/storage.py`). The row (`transaction_attachments`: filename, `mime_type`, size) is the truth; the bytes are in storage under `{user_id}/{attachment_id}`. **Storage is a swappable interface** (`Storage`: put, get, delete, list): `S3Storage` (boto3 in a thread, path-style addressing, any S3-compatible store: AWS S3, Cloudflare R2, MinIO, floci in development) is used when `ATTACHMENTS_S3_BUCKET` is set (plus `..._ENDPOINT`, `..._REGION`, `..._ACCESS_KEY_ID`, `..._SECRET_ACCESS_KEY`), otherwise `LocalStorage` (a folder, `ATTACHMENTS_DIR`, `/data/attachments` in the image, a volume in `docker-compose.prod.yml`, which the API and the worker both mount). `just storage-up` starts floci and `python -m app.admin create-bucket` makes the bucket. Tests replace the store with `set_storage` (a temp folder, autouse in `test_attachments.py`), and `S3Storage` is tested against moto. **Upload goes through the API**: `POST /transactions/{id}/attachments?filename=` takes the file as the raw request body (not multipart; 10 MB, `ATTACHMENT_MAX_BYTES`; at most 10 per transaction), `GET /transactions/{id}/attachments`, `GET /attachments/{id}` (inline, `?download=true` forces a download; `nosniff`) and `DELETE /attachments/{id}`; another user's row or transaction is a 404. **The type is decided from the file's bytes** (`detect_mime_type`), never from a header, so an SVG or HTML file cannot be passed off as an image; filenames are cleaned. **The file is written first and the row second**, and a failed insert deletes the file; deleting removes the row, then the file, best effort. A trashed transaction keeps its files but takes no new ones. Hard-deleting a transaction, an account or a user cascades the rows only, so the daily `purge_orphan_attachments` job (04:30) lists storage and deletes files older than 24 hours with no row (anything not named like our keys is left alone); no other code path touches storage for cleanup. A transaction response carries `attachment_count` (a `column_property`, like `refunded_amount`). **Backups do not include attachments** (`transaction_attachments` is in `EXCLUDED`; the Backup card says so): back up the bucket or the volume with its own tools. Web: `AttachmentsField` and `useAttachments` in the transaction form (on a saved transaction files go up and come off at once; on a new one they wait in `pending` and upload after it is created, from `TransactionForm`'s submit), `lib/attachments.ts` (limits, `checkFile`, `uploadAll`), the browser reaches files through `routes/api.attachments.ts` and `routes/api.attachments.$id.ts` (both use `utils/proxy.ts`), and a paperclip shows on the row.
- **Web links on a transaction** (`models/link.py`, `services/link.py`, same router as attachments, `TransactionLink`) sit beside the files in the Attachments section: `GET` and `POST /transactions/{id}/links` (`{url, title?}`) and `DELETE /links/{id}`, at most ten per transaction (`LINKS_PER_TRANSACTION`). They are a **separate table**, not a kind of attachment, so that, unlike files, **links are in the backup** (`transaction_links` is an owned table). `normalize_url` is the one rule: trimmed, `https://` added when no scheme is typed, **http or https only** (`javascript:`, `data:`, `mailto:`, `ftp:`, `file:` are refused, and a bare `host:port` is still a host), a host with a dot (or `localhost`), no spaces, no embedded user name or password, at most 2000 characters. **Nothing on the server ever fetches a link** (no title lookup, so no SSRF); a link is only shown as `<a target="_blank" rel="noopener noreferrer">`. A trashed transaction keeps its links but takes no new ones. A transaction response carries `link_count` next to `attachment_count`; the paperclip on a row counts both. Web: `useLinks` (same pending-until-saved behaviour as files), `LinkAdder` (not a `<form>`, because it sits inside the transaction form: Enter adds the link and is kept from submitting the transaction), `lib/links.ts` (`parseUrl` mirrors the API's rule), and after a new transaction's files and links go up the list is invalidated again so the paperclip appears.
- **Bank and account number** on an account (`accounts.bank`, `accounts.account_number`, both optional) tell apart accounts that share a name (several savings accounts at one bank differ only by number) and are what a bank statement will be matched to (the number is in a statement's file name). `bank` is free text (the web form suggests the banks already used plus a short list, `BANKS` in `lib/accounts.ts`). The number is **normalised on the way in** (`normalize_account_number`: spaces removed, upper-cased, letters, digits, `*` and `-` only, at most 34 characters, so a masked card number like `533294XXXXXX4164` or an IBAN fits and a full card number is not encouraged); blank becomes null. **A user's accounts cannot share a number** (unique constraint `uq_accounts_user_account_number`, plus a friendly 409 from `_check_number` naming the account that has it); any number of accounts can have none, and other users are unaffected. The number is shown **in full, never masked** (chosen over last-4 masking), in the account cards, the account pickers (`accountMenuItems`, the transaction filter) as `Name · Group · Currency · BML · 7730000486374`, and `AccountRef` (inside transactions and templates) carries both. The accounts search (`q`) also matches bank and number, ignoring spaces. They are in backups automatically and in the seed (made-up numbers).
- **Transaction groups** (`models/group.py`, `services/group.py`, `routers/group.py`, table `transaction_groups`) bundle a handful of related transactions under a name and show what they add up to (a trip over several accounts, instalments, a treatment bought over weeks, an expense plus what a friend paid back). **A group changes nothing else**: the transactions keep their category, tags and amounts and every other total ignores groups. The link is a nullable `transactions.group_id` (`ON DELETE SET NULL`), so **a transaction is in at most one group** and deleting a group only unlinks; `Transaction.group` loads with the row and `TransactionResponse.group` is `{id, name}`. **A group holds 2 to 50** (`MIN_GROUP` / `MAX_GROUP`): creating needs two to fifty ids, adding stops at fifty, and **a group left with fewer than two is deleted**, both when transactions are taken out (`POST /groups/{id}/transactions/remove` answers `{removed, dissolved}`) and when one is deleted for good or turned into a transfer (`GroupService.dissolve_undersized`, called from `TransactionService.delete`, `bulk_purge` and `update`). A member must be yours, **not in the trash, not a transfer and not in another group** (a 422 saying which); a transfer that a member is edited into leaves its group. The summary (`GroupResponse`: `transaction_count`, `date_from`, `date_to`, `money_in`, `money_out`, `net`, base `currency`) counts **live** transactions for the count and dates, and **only `counted()` ones** (posted, not planned) for the money, in `base_amount`; income is money in (a refund is income, so it lowers the net) and expenses money out; a trashed member stays linked and comes back counted on restore. Routes: `GET/POST /groups` (list newest activity first, `q` over name and note, `X-Total-Count`), `GET /groups/{id}` (summary plus its transactions as `TransactionResponse`s), `PATCH` (name, note; `note: null` clears), `DELETE`, `POST /groups/{id}/transactions` (add). **There is no transaction-list filter by group** (it would need threading through six routes): the group dialog lists its members instead. Groups are in backups (`transaction_groups` is an owned table; ids are remapped like everything else) and the seed does not make one. Web: a "Group" button in the selection bar (`GroupDialog`: a new group, or add to an existing one; needs 2 to 50 selected to create), a blue group chip on each row that opens `/groups?group=<id>`, the Groups page (`routes/_protected/groups.tsx`, in the Organise nav group, icon `inventory_2`) and `GroupDetailDialog` (summary, members each with a take-out button, edit, delete). `folder_open` is **not** in the bundled icon font; check any new Symbol name against it.
- **Credit limit, exclude from stats and balance adjustment** (account polish). **Credit limit:** `accounts.credit_limit` (non-negative, in the account's currency) only for `CREDIT_LIMIT_GROUPS` (cards and overdrafts; a limit on another group is a 422, and moving an account out of those groups clears it). It **changes no balance**: you track a card as money owed (a negative balance), so the web just shows owed against the limit (`creditUsage` in `lib/accounts.ts`: a bar and percent on the account card, and a "Credit used" card on the dashboard when any account has a limit). **Exclude from stats:** `accounts.exclude_from_stats` leaves the account out of **everything that sums across accounts** (the account summary, net worth and the balance trend, which skip it like archived ones, and, through `Transaction.reported()`, the list totals, category totals, the budget's activity and the monthly stats), while its own balance, transactions, snapshots and its row in every list stay. **`Transaction.reported()` is `counted()` less balance adjustments and less excluded accounts, and is what any income or spending sum must use now**; `counted()` stays for balances, snapshots, goals, groups and subscriptions. `reported(include_excluded_accounts=True)` is used when the totals are filtered to one account, so looking at the excluded account itself still shows its figures. `AccountRef` carries `exclude_from_stats`, the transaction list marks such rows "Not in my totals", and the totals card says that excluded accounts and adjustments are not counted (`excludedNote`). **Balance adjustment:** `POST /accounts/{id}/adjust` with exactly one of `new_balance` (what the bank shows; the difference is worked out from the balance now) or `amount` (signed), an optional `date` (default today; earlier dates change the history from then on) and `note`. It records a transaction with **`adjustment=true`**: an income if the balance was too low, an expense if too high, in the account's currency at its rate, category "Balance adjustment" (`ADJUSTMENT_CATEGORY`), method other, description "Balance adjustment" unless a note is given. It moves the balance, the history and the snapshots (so it is stale-marked like any past transaction) but is **left out of every report** (`reported()`). **An adjustment is never edited** (a PATCH is a 422 saying to delete it and make a new one; bulk edit skips it), **cannot be refunded or put in a group**, can be trashed (which undoes it), and an archived account refuses one. Only this route makes them: `TransactionCreate` has no such flag. The web: a Tune button on the account card opens `AdjustBalanceDialog` (set to balance, or add or take away, with a live preview from `adjustmentPreview`), and an adjustment row shows an "Adjustment" tag with only a Delete button.
- **Statement import** (`app/statements.py`, `services/imports.py`, `routers/imports.py`, tables `import_batches`, `import_rows`, `import_aliases`, columns `transactions.import_batch_id` and `import_ref`). A bank's CSV is read by a **profile** chosen from the header row (`statements.detect`): `bml` (separate Debit/Credit columns; the real date and time are inside the description, not the posting date) and `mib` (one signed amount; a `**B/F Balance` line is the opening balance, not a transaction). `parse_statement` is pure and returns rows with a positive amount, a direction, the counterparty, the bank's reference and running balance; an unknown or unreadable file is a `StatementError`, a plain-words 422, never a crash. **A new bank is a new parser in `_PARSERS` plus a `detect` rule.** Real statements hold real names and numbers: **never put one in the repo**, fixtures in `tests/data` are made up. Two steps, nothing saved until the second: `POST /imports/preview?account_id=` takes the file as the raw body (2 MB, 2,000 rows) and returns each row with what Maalu knows (a suggested vendor and its default category and tags, a remembered own-account transfer, a duplicate flag) plus a **balance check** (what the account would hold after importing against the statement's closing balance); `POST /imports` takes the rows the user confirmed and makes them as one batch. **Re-importing is safe**: rows whose bank reference was already imported into that account (live transactions only, so an undone import can be done again) are skipped (`reference`), a row that is the other side of a transfer between your accounts already recorded (same amount, within a day) is flagged `transfer` and left out by default, and a hand-entered transaction with the same day, amount and direction is flagged `possible` but kept. Rows go through `TransactionService.create`, in the account's currency, payment method from the bank's type (purchases are debit card, the rest bank transfer), category `Uncategorized` when none is given; a row marked as a **transfer** (`transfer_account_id`, same currency only) becomes a transfer to or from the statement's account, and the choice is **remembered** (`import_aliases`: a normalised statement name to a vendor or an own account, one row per name, followed by vendor merge) so the next statement fills it in; a vendor whose own name equals the statement name is found without an alias. **One bad row never fails the import**: each row runs in a savepoint, a rule error or any exception becomes that row's `failed` with a reason, and the rest go in. Every row sent is logged in `import_rows` (`imported`, `skipped` already there, `left_out` by the user's choice, `failed`) and `GET /imports/{id}/report` returns it as a **CSV report** (Row, Date, Time, Type, Amount, Counterparty, Description, Reference, Result, Reason; text starting with `= + - @` is prefixed with `'` against spreadsheet formulas); the web offers it in the result dialog and the history. `DELETE /imports/{id}` **undoes** the batch (its live transactions go to the trash through `bulk_trash`; ones you already deleted are left). `GET /imports` is the history (`transaction_count` is how many are still live). Batches, aliases and rows are in backups. Web: the Import page (`routes/_protected/import.tsx`, Money group in the nav) with `UploadCard` (the account is guessed from its number in the file name, `accountForFilename`), `ImportReview` (state in `useReview`; every row, **search and amount-range filtering done in the browser** with `filterRows`, since a statement is at most 2,000 rows; a pencil on each row **edits its vendor and category in place** (`WillBeCell`; its "also the N other rows named …" box, on by default, carries the change to rows the bank named the same way, like the bar's switch); a bulk `AssignBar` for vendor and category, "also rows with the same name", "Select all N matching" the filter, mark as transfer, leave out; `lib/imports.ts` holds the pure `patchRows`, `commitRows`, `countRows`, `filterRows`), `ResultDialog` and `HistoryTable`. The browser reaches the API through `routes/api.imports.preview.ts` and `routes/api.imports.$id.report.ts` (`utils/proxy.ts`). Not built yet: more banks, "create a rule from this", Excel files, converting between currencies.
- **Notifications** (`models/notification.py`, `services/notification.py`, `routers/notification.py`, table `notifications`) are things in your data worth a look, found by `NotificationService.sync` and kept as rows you can read and dismiss. Three kinds, each with a switch on the user (`notify_payments`, `notify_budget`, `notify_goals`, all default on, set with `PATCH /users/me`, in backups): **payments** (a planned transaction, live, dated within `DUE_SOON_DAYS` (3) ahead or already past: `payment_due`, and later a separate `payment_overdue`), **budget** (a line of the *current* period that is `warning` or `over`, one per line, period and status) and **goals** (`goal_reached`, once). **It is derived, never entered**: every event has a `dedupe_key` (`due:<transaction id>`, `overdue:<id>`, `budget:<line id>:<period start>:<status>`, `goal:<id>`), unique per user, and `_add` makes one only if the key is unseen (a parallel look that loses the race is refused by the unique constraint inside a savepoint and ignored), so looking again never repeats. **Dismissing keeps the row** (`dismissed_at`, hidden from lists and counts) so a dismissed event is not announced again; reading sets `read_at`; `purge_old` sweeps anything older than 90 days. It is looked for by the daily `generate_notifications` job (04:00 UTC, which also sweeps) **and on read** for one user (`GET /notifications`, `/notifications/unread-count`), throttled to once per `SYNC_EVERY_SECONDS` (5 minutes) per process (`_last_sync`; tests set it to 0), so the bell is right with no worker running. **The time is noted when a look finishes, not when it starts**: the bell's count and the list load in parallel, and noting it first made the second skip the look and read before the first committed (a count of 1 over an empty list, found by an end-to-end test); two looks at once are safe because the unique key makes the second wait and make nothing twice. **Writing a transaction (create, update, trash) and making a salary task clear the user's throttle** (`notification._last_sync.pop`), so news that comes from your own change (a bill that makes the money run short) shows at the next read, not up to five minutes later. Routes: `GET /notifications` (`unread=true`, paged, `X-Total-Count`), `GET /notifications/unread-count`, `POST /notifications/read-all` (declared before `{id}`), `POST /notifications/{id}/read`, `DELETE /notifications/{id}` (dismiss). **Notifications are not in backups** (`notifications` is in `EXCLUDED`: they are worked out again). Web: the bell in the top bar (`NotificationBell`, badge from the `_protected` layout's loader through `unreadCountFn`, so it refreshes after every action and on tab focus; a popover with the newest eight, clicking one marks it read and opens its `link`), the Notifications page (`routes/_protected/notifications.tsx`, reached from the bell's "View all", not in the nav) and `NotificationSettings` (the three switches) on the Settings page. The type is `AppNotification`, because `Notification` is the browser's own. **Email is not built**: a new delivery would read the same rows. A new kind needs a generator in the service, a `kind` in `schemas/notification.py` and `KIND_META`, and (if it should be switchable) a flag on the user.
- **Installments and reminders** (on `subscriptions`: `installments_total`, `remind_days_before`). **Installments:** `installments_total` (1 to 600, null = goes on) makes a plan with a fixed number of payments. `payments_made` is the count of **posted payments linked to it** (`counted()`, so a payment made by hand counts and a skipped, deleted planned one does not), `installments_left` is the rest (null when ongoing). `SubscriptionService.sync` sets the status to **`completed`** (a new `SubscriptionStatus`, never chosen in the web form unless it already is) once `payments_made >= installments_total`, trashes any leftover planned payment and plans nothing more; a skipped payment is not used up, the next cycle is planned and it still needs paying. Raising the total above what was paid, or clearing it with an explicit `null`, **reactivates** a completed plan in `update`; lowering it to what was paid completes it on the next look. A completed plan is left out of the active count and monthly cost, and the notification `installments_done` ("<name>: last payment made", once, under the payments switch) tells you. **Reminders:** `remind_days_before` (0 to 60, default 3, null = never) is how many days ahead of a payment its `payment_due` notification is made; **overdue is always told**. `NotificationService._payments` looks `MAX_REMIND_DAYS` (60) ahead and applies the subscription's own lead, and a planned payment that belongs to no subscription keeps the fixed `DUE_SOON_DAYS` (3). An explicit `remind_days_before: null` on create is kept empty on purpose (the column's default would otherwise fill it in). Web: `SubscriptionForm` has "Number of payments" and "Remind me" (`lib/subscription.ts`: `REMIND_OPTIONS`, `remindToField`, `installmentsText`), the table and cards show "3 of 12 paid", and `completed` has its own status chip. Not built: candidate detection and auto-record, email reminders.
- **Linking two transactions into one transfer** (`models/transfer_dismissal.py`, `services/transfer_link.py`, `routers/transfer_link.py`, table `transfer_dismissals`) fixes a move of your own money entered twice (an expense in one account and an income in another). `GET /transactions/transfer-suggestions` scans for pairs: same amount and currency, different accounts, within `SUGGEST_WINDOW` (2 days), both live, posted, not adjustments and with an account; the expense has no items or refunds and the income is not a refund; each row is in at most one suggestion (closest wins). **The scan only suggests; nothing merges until the user confirms.** `POST /transactions/link-transfer {expense_id, income_id}` turns the **expense row into the transfer** (keeps its date, amount, account and notes; `to_account` and `to_amount` come from the income; category, vendor and subscription are dropped like any edit into a transfer; tags of both are kept; the income's description is used only when the expense has none) and **trashes the income** (so undoing is a restore plus an edit). Balances do not change; income and expense totals drop by the pair. `POST .../dismiss` ("Not a pair") remembers a pair in `transfer_dismissals` (idempotent; in backups). The routes are mounted before the transaction router. A cross-currency pair can only be linked by hand (the suggestion needs the same currency). Web: `TransferSuggestionsCard` (accordion, closed by default, above the list), and a "Make a transfer" button in the selection bar when `linkablePair` (`lib/transfer-link.ts`) finds exactly one expense and one income in different accounts, with `MakeTransferDialog` to confirm.
- **Net worth drivers** (`GET /stats/net-worth-drivers?from&to`, `StatsService.net_worth_drivers`, `schemas/stats.py: NetWorthDrivers`; web `/net-worth`, `routes/_protected/net-worth.tsx`, `lib/net-worth.ts`, `components/charts/Waterfall.tsx`, `components/net-worth/AccountsTable.tsx`, Money group, icon `finance`) says **how net worth moved over a period and what moved it**. Net worth is the same line as the balance trend: the sum of what the **active accounts that count toward stats** are worth in the base currency (`_in_scope`: not archived, not `exclude_from_stats`; a debt counts below zero). The start is the worth **at the end of the day before `from`** and the end the worth at the end of `to` (`_worth_on`: a stored snapshot for a completed day, each at the rate it had, else worked out live at the current rate; a day before an account's first snapshot counts its opening amount at the current rate, as in the trend). The change is split into **five drivers that always add up to it exactly**: `income` (not refunds), `spending` (expenses less refunds), `adjustments` (balance corrections, shown apart because `reported()` leaves them out), `transfers` (only a transfer across the edge of net worth counts: one between two accounts that count is the same amount out and in, so it cancels; one to or from an archived or excluded account changes it) and `exchange_rates`, **the remainder** (`change` less the four flows, each flow taken at the `base_amount` it was made at), which is the effect of foreign-currency accounts being worth a different amount when their rate changes and is zero when everything is in the base currency. Flows use `counted()` (no planned, no trashed) restricted to accounts in scope, so they can differ from the dashboard's income and spending, which also include archived accounts. The response also lists each account's own start, end and change, biggest first, leaving out accounts that are empty at both ends. `from` after `to` is a 422. Web: a period picker (`PeriodPicker` with `single`, the same presets as Compare but one range; **the default is the last 30 days**, which is always a full month of days), a sentence (`netWorthSentence`: what it did, what you kept, which other drivers moved it), start, end and change cards, and a **waterfall** (`Waterfall`, `waterfallBars`): each driver that is not zero floats from where the one before ended, starting at zero (where you stood), then the total change, with the income colour for what added, the expense colour for what took away and the line colour for the total, an arrow and a signed figure on every bar, and a table toggle. The axis is the change since the start, not net worth itself, so the steps are not dwarfed by a large total. Not built: a driver for interest or fees, splitting exchange rates per currency, and comparing two periods' drivers.
- **Trends** (`/trends`, `routes/_protected/trends.tsx`, `lib/trends.ts`, `components/trends/TrendsTable.tsx`, Money group, icon `calendar_month`) is the category-by-month table: one row per category, one column per month, a Total and a Per month column and an "All categories" footer, Spending or Income, over 6, 12 or 24 months ending with this one. It reads **`GET /transactions/categories/monthly`** (`date_from`, `date_to`, `account_id`; default the last 12 months, at most 36, 422 beyond that; declared before `/{transaction_id}`): the **same numbers as `/transactions/categories` split by month**, because both go through one routine, `TransactionService._category_buckets(conditions, family, monthly=)`, so the rules cannot drift apart (`reported()`: no transfers, adjustments, planned, trashed or excluded accounts; a split transaction counts under each item's category with its base amount shared by `allocate_base`; a refund takes away from spending in the month it arrives). The response lists **every month in the range** (`months`, "YYYY-MM") and each category's `amounts` is dense and lines up with it (zero where nothing happened, all quantised to four decimals so the strings agree), `total` is their sum; the month comes from `extract(year/month)` in SQL for plain rows and from the transaction's date for split ones. The range is whole calendar months even when the dates are not. In the web a cell is shaded by its share of the biggest figure in the table (`heat`, `color-mix` over `--chart-expense` or `--chart-income`) and always shows its number, so shade is never the only signal; zero is "–", a refund-heavy month can be negative and is unshaded; the table scrolls sideways with the category names kept in view (it is a matrix, so it does not go through `ResponsiveTable`'s card view). Totals per month are added exactly (`sumDecimals`); the average is display-only. A **Table / Chart toggle** (`view=table|chart` in the URL) shows the same data as **stacked columns** (`components/charts/StackedColumns.tsx`, `stackSeries` in `lib/trends.ts`): one column per month, the 6 biggest categories (a lone seventh is not hidden) stacked biggest first at the bottom and the rest folded into a grey "Other" on top, a 2px gap between segments, a legend, and a readout on hover or focus listing the column's segments and its total. A column cannot show a negative figure, so a category's refunds past its spending count as zero in the chart (the table is exact, and the chart says so). **Categories can share an accent, so the chart recolours**: `distinctAccents` keeps a category's own accent for the first series that has it and gives a repeat the first accent no series in the chart owns, so every segment is told apart (a chart segment can therefore differ from that category's dot elsewhere). Below the table a **Needs and wants by month** table (`kindMonths`, `components/trends/KindMonthsTable.tsx`, spending only, table view) adds each kind's category rows exactly. Not built: an account filter in the page (the API has it), a pivot of other dimensions (tag, vendor, account), small multiples (a line per category).
- **Available to spend** (`GET /stats/available-to-spend`, `services/available.py: AvailableService`, `schemas/available.py`; web: `components/dashboard/AvailableCard.tsx`, `lib/available.ts`) answers "what can I spend until the end of the budget period without touching a bill or money I set aside", the number the user used to work out in a spreadsheet. **Available = spendable balance - bills still to pay - credit card statements due by the period end - money set aside by hand**, all in the base currency. **Spendable balance**: accounts that count toward net worth (not archived, not `exclude_from_stats`; `StatsService._in_scope` and `_worth_on` at today's rate) in `SPENDABLE_GROUPS` (cash, accounts, debit card, prepaid) **and not followed by a goal**; savings, investments and the accounts a goal follows are listed as `kept_apart` (their money is already earmarked or not for spending), and cards, overdrafts and loans are neither (what you owe is not money to spend). **Bills still to pay**: live, **planned** expenses (no adjustments) dated **up to the end of the current budget period** (`period_bounds` with `period_start_day`), **overdue ones included and listed first** (`overdue`), paid from a spendable account or from none yet (a planned bill on a card is not counted); a subscription's next payment is one of these, so paying it (`POST /transactions/{id}/post`) or skipping it (deleting it) changes the figure. **Set aside**: goals tracked by hand (`mode == "manual"`), their `saved` amount, which is assumed to sit inside the everyday accounts; a goal that follows an account needs no subtraction because that account is already left out. **Planned income** up to the period end is returned as `expected_income` and **never counted**, so the figure does not rely on money that has not arrived. The result can be negative (shown as "Short"). Web: a card at the top of the dashboard with the number (orange and a "Short" chip when below zero), the sum in words (`workingLine`: "MVR 18,585.08 in 1 account, less MVR 330.69 for 2 bills and MVR 15,000.00 set aside for 1 goal"), and "Show the working" (what each account holds, each bill with its date or "overdue", each goal's amount, and the planned income note); a new account is told to add an everyday account. It is for the **current** budget period only (the dashboard's month picker does not move it). **The Month plan page** (`/plan`, `routes/_protected/plan.tsx`, Planning group, icon `checklist`; `lib/plan.ts`, `components/plan/*`) lays the same data out by day: four tiles (you have, bills to pay with the overdue count, set aside, available or **short by**), a verdict sentence ("The money runs out at Wifi Bill (06 Nov 2026)"), **Bills by day** (overdue together first, then each day, each bill with its account, subscription and **what is left after it**, a running figure from `startingPoint` = balance less set aside; the first bill that goes below zero gets a "Short from here" chip) and a side column (accounts it counts, goals set aside, accounts kept apart). Planned **income** is listed on its day as "Expected · not counted" and never changes the running figure (`AvailableToSpend.expected`, same shape as `bills`; `AvailableBill.account` names the account). Each row has **Mark as paid** (or **Received** for income) through `MarkPaidDialog`, which for income says "Mark as received" and "Amount received" because **a salary is never exactly what was planned**: the amount is pre-selected and the real one typed in before saving. The page reads `getAvailableToSpendFn` and `listUpcomingFn` (for the full transactions the dialog needs) and is linked from the dashboard card ("Open the month plan"). **Choosing which accounts are spendable:** `accounts.spendable` (null = what the group says, true or false = your choice; `PATCH /accounts/{id}` with `null` goes back to the group) and `is_spendable(group, override)` in `app/enums.py`, which `AvailableService` uses instead of the group test alone; `AccountResponse` has the raw `spendable` and the effective `counts_as_spendable`. **What is owed never counts** (a `true` on a card, overdraft or loan is a 422, and moving an account into those groups clears the choice), and **a goal that follows the account still keeps it apart** whatever the choice. Bills planned on an account kept apart are not counted, as before. Web: one switch, "I spend from this account" (`SpendableField`), on the account form for groups that are not owed: it shows what the group says until touched, and `spendableValue` sends `null` while it is untouched or back at the group's answer, so only a real difference is stored. **Planned transfers** (`AvailableService`, `AvailableBill.transfer`): a planned transfer **out of an everyday account to an account that is not one** (savings, a loan, a card) is a bill, since that money is no longer yours to spend (title: its description, else "Transfer to <account>"; amount: its `base_amount`; the row on the plan carries a "Transfer" chip and **Mark as done**, and `MarkPaidDialog` shows only the day and time for a transfer and sends no amount, so the planned amount stands). A move between two everyday accounts changes nothing, money arriving from savings is **never counted and not listed** (like planned income, and it would muddy the expected-income sentence), and **a planned repayment into a credit card whose statement is already a `card_payments` row is left out** so it is not counted twice (a repayment into a card with no statement in the plan does count). Not built: recurring income that is not yet planned (it could not change the figure, since income is never counted; it would need subscriptions to run both ways), a split of a planned transfer, offering the salary split when a planned salary is marked received. **A "Coming up" card on the dashboard** (`components/dashboard/UpcomingSoonCard.tsx`, beside Latest transactions) lists the next five planned items (overdue in red, "and N more", link to `/plan`) from `listUpcomingFn`. **A notification when the money runs out** (`NotificationService._money_short`, kind `money_short`, under the payments switch): the bills still to pay, in plan order, are taken off what the everyday accounts hold less what is set aside, and the first bill that takes it below zero is named ("The money runs out at Wifi Bill", "Short by MVR X after it, due 06 Nov", link `/plan`, key `short:<period start>:<bill id>`); with no everyday account there is none.
- **Salary split** (`models/salary_rule.py`, `services/salary_split.py`, `routers/salary.py`, `schemas/salary.py`; table `salary_rules`, columns `transactions.split_from_id` and `goal_entries.split_from_id`) divides a salary between accounts and goals when it arrives. **Rules** (`/salary-rules`, `SalaryRule`): each account or goal has **at most one** rule (unique per user), a `mode` (`percent`, 0 to 100, or `fixed`, an amount in the salary's currency) and a `value`; deleting the account or goal deletes the rule. **Nothing happens by itself**: `GET /transactions/{id}/salary-split` returns a **plan** (every rule worked out, percentages of the salary rounded half-even to 4dp, with `ok` and a plain `reason` for a line that can't be made, `total`, `left`, `over`, and `made` once it was applied), the web shows it for the user to edit and confirm, and `POST` with the lines **the user confirmed** makes it. Only a **posted income in the Salary category with an account** can be split (else 422). A line's destination: an **account** target is a **transfer** from the salary's account (dated the salary's, described "From salary: <name>"); a **goal that follows an account** is a transfer into that account; a **goal tracked by hand** gets an amount set aside (`goal_entries`, note "From salary", only when the salary is in the base currency). **Refused or skipped** (422 on apply, `ok: false` in the plan): the account the salary arrived in, an archived account, **another currency than the salary's account** (cross-currency splits are not built), a goal in a different currency than the base. **Apply re-checks everything and trusts only the targets and amounts**: no duplicate targets, amounts positive, the total **not above the salary**, nothing half-made (the request's transaction rolls back). **A salary is split once**: a second `POST` is 409 until it is undone; `DELETE` **undoes** it (the made transfers go to the trash through `bulk_trash`, the set-asides are deleted; 409 when nothing was split). The links back are `split_from_id` (`ON DELETE SET NULL`, in backups with the rest); `salary_rules` is an owned table. Changing or trashing the salary afterwards does not touch what the split made. Web: Settings has `SalaryRulesCard` ("When my salary arrives", `SalaryRuleDialog` to add or change a rule, "Together: 20% of the salary + MVR 1,500.00"), the transactions page loads whether any rules exist and **adding a posted Salary income opens `SalarySplitDialog` by itself** (`useSalarySplit.afterCreate`, `TransactionForm`'s `onCreated`), a "Split salary" button on every salary row opens it later (`canSplitSalary`), the dialog lists each line with a tick and an editable amount (`lib/salary.ts`: `splitLines`, `splitTotals` exact with BigInt, `splitRequest`), says what stays in the account, blocks sending more than the salary, and for a split salary shows what was made with "Undo the split". **Pending approvals and automatic rules** (`models/salary_split_task.py`, table `salary_split_tasks`, `salary_rules.auto`): a split no longer depends on the dialog being answered when the salary is saved. **`SalarySplitService.on_posted`**, called by the transaction routes after **create, update and post** (not by services, which would make a cycle, and not by imports), queues a task (`pending`, one per salary, unique on the transaction) for a **posted income in the Salary category with an account** when the user has at least one rule; a planned salary only queues once it is posted or marked received (so the split is worked out from the amount that really arrived). **Each rule has `auto`, off by default**: a line whose rule is automatic is **made at once** by `on_posted` (inside a savepoint; if any automatic line can't be made, or the automatic lines would add up to more than the salary, **none** is made by itself and everything waits with the reason), and the task stays pending for the lines that ask. **A salary's split is now made line by line**: a plan item has `done` (its account got a transfer or its goal an amount) and `auto`, `made` lists what was made, `complete` is every rule done, and `total`, `left` and `over` count what is already made against the salary; `POST .../salary-split` makes only the lines sent, refuses a line already made (409 when every line sent was already made, 422 naming it when mixed) and checks made plus new against the salary; `DELETE` undoes everything made and **puts the task back to pending** (it is not made automatically a second time). A task is `done` when no line that can be made is left (`_settle_task`, also when listing), and `dismissed` by `POST /salary-split-tasks/{id}/dismiss` (the salary can still be split by hand). Routes: `GET /salary-split-tasks` (pending ones with their plan; a trashed or changed salary is skipped), `GET /salary-split-tasks/count` (the badge; counts pending tasks on live, posted transactions) and the dismiss route. `salary_split_tasks` is an owned table in backups. Web: a **Pending page** (`/pending`, Planning group, icon `task_alt`, `routes/_protected/pending.tsx`, `components/pending/PendingSplitCard.tsx`) lists each waiting salary with what was already moved automatically, what waits (with each line's rule and any reason it can't be made) and **Approve** (makes every line that can be made, as proposed), **Review and edit** (the same `SalarySplitDialog`, which now shows made lines as "Already made", counts them against the salary, offers "Undo what was made" and says "Finish splitting this salary") and **Dismiss**; a **red count beside Pending in the sidebar** (`pendingSplitCountFn` in the `_protected` loader, `SideNavItem`'s `badge`); a switch "Move it automatically when a salary arrives" in the rule dialog and a "Moves automatically" chip on the rule. The dialog still opens by itself after a Salary is added (a prompt, not a move). **A notification** `split_waiting` ("A salary split is waiting", link `/pending`, key `split-waiting:<task id>`, under the payments switch, made by `NotificationService._split_waiting` for a pending task on a live posted salary; it stays once seen and is not made again). **Marking a planned salary received offers the split**: `MarkPaidDialog` takes `onPaid(transaction)` and `UpcomingCard` and the Month plan call `useSalaryOffer` (`lib/use-salary-offer.ts`), which opens `SalarySplitDialog` after the post when the paid transaction is a salary in an account and rules exist (the host lives in the page, since the paid row leaves the lists). Not built: other currencies, categories as targets (the budget is limits, not envelopes), a trigger on other things than salary.
- **The Salary category** (`categories.is_salary`, `SALARY_CATEGORY = "Salary"` in `app/enums.py`) is the one **default category**, for pay. Every account has it: made at registration (`UserService.register` → `CategoryService.ensure_salary`), made again on `GET /categories` when missing (data cleared, an old backup), and a category already called Salary is adopted (the migration flags existing ones; `get_or_create` flags a plain one it finds). - **Needs and wants** (`categories.kind`, `CategoryKind` in `app/enums.py`: `need` or `want`, null = **not sorted**). - **Rate refresh and rate history** (`services/exchange_rate.py`: `cache_latest`, `refresh_rates`, `rate_history`; `accounts.auto_rate`). Past days are cached in `exchange_rates` (a past day never changes); today and future days get the latest rate, uncached; a day with no data gets the nearest earlier one (`exact: false`). If the source is down the field just stays empty, as before.

Models use a deterministic constraint `NAMING_CONVENTION` (`models/base.py`), and enums are stored as non-native strings (`native_enum=False`, `values_callable`). Keep both conventions when you add columns, so autogenerated migrations stay clean. Ruff excludes `migrations/versions`.

## Web architecture (`apps/web/src`)

- **The browser never talks to the API.** Everything goes through TanStack server functions in `src/server/*.ts`, which call `apiRequest()` (`server/api.ts`). That function attaches the JWT from an encrypted httpOnly session cookie (`utils/session.ts`) and calls `API_URL/api/v1...`. The one exception is file download: `routes/api.export.transactions.ts` is a server route that forwards a fixed set of filters along with the token.
- `apiRequest` retries a **GET** once when the connection fails: the API closes idle kept-alive connections, and reusing one just closed fails with `ECONNRESET`, which showed as "Cannot reach the Maalu API" now and then. A write is never retried (it might have been applied).
- Server functions validate input with Zod and **return `ApiResult<T>` values** (`{ok, data, total?}` / `{ok:false, status, error}`) instead of throwing, so errors survive serialisation. FastAPI `detail` errors are flattened into readable strings.
- Route loaders call server functions and `unwrap()` the results (a 401 redirects to `/login`). Mutations go through `useAction().run(...)` (`lib/use-action.ts`). It handles pending and error state, sends a 401 to `/login`, and on success calls `router.invalidate({ sync: true })` to refetch **all** route data. Don't add per-query caches.
- Protected pages live under `routes/_protected/`. The `beforeLoad` guard there is for UX only, because server functions and the API check auth again. List state (page, pageSize, q, filters) lives in URL search params validated by Zod `validateSearch`, with `loaderDeps` passing it to the loader. See `lib/pagination.ts` (`pageSearch`, `lastPageIfOutOfRange`) and `lib/transaction-filters.ts`.
- **API types are generated, never hand-written.** The API's OpenAPI schema is the one source of truth: `just api-types` writes the committed `apps/web/openapi.json` (from `python -m app.openapi`) and `src/types/api.generated.ts` (openapi-typescript with `--enum-values`, run through `pnpm dlx` because it needs the TypeScript 5 compiler API and the app uses TS 7). `src/types/api.ts` is a thin layer of short names over it (`Transaction = components["schemas"]["TransactionResponse"]`), re-exports the generated enum arrays (`PAYMENT_METHODS = paymentMethodValues`) and holds the web's own display labels (`Record<Enum, string>`, so a new enum value is a type error until it gets a label). Never describe a response shape by hand in `api.ts`: change the Pydantic schema (field docs go in `Field(description=...)`, which reach the generated types), run `just api-types`, and add an alias if the web needs a new type. **Run `just api-types` after every API schema change and commit the two generated files with it**; `just check` runs it first. CI never regenerates, it fails if either committed file is stale (`just check-openapi`, `just check-generated-types`). Pure helpers in `src/lib` have vitest tests (`just test-web`); run `pnpm --filter @maalu/web test` rather than `pnpm exec vitest`, whose output the RTK hook swallows.
- Transaction form entry speed: the form starts from a `TransactionSeed` (`components/transaction-form/request.ts`), made from an edited transaction, a duplicate (`seedFromTransaction`, the old rate dropped so the market rate is suggested), a template (`seedFromTemplate`) or what was just saved (`seedAfterSave`, which keeps account, category, vendor and method and clears the amount and note). The controlled fields live in `useFormFields`; the uncontrolled ones take their defaults from the seed and remount when `round` changes. "Add another" keeps the dialog open after a *new* transaction, "Save as template" reads the form into a template, and the Transactions page has a Duplicate button on every row. Child components take a `seed`, never the `transaction`, so only `request.ts` and the form itself know whether it is an edit.
- Category colours in the web: `lib/categories.ts` (`categoryAccent`, `categoryPath`, `parentChoices`), `CategoryDot` beside names (Categories page, transaction subtitle, `CategoryBreakdown` bars), `ColorSwatches` and a parent select in `CategoryForm` (colour left empty on a new category = automatic). The Categories page indents sub-categories under their parent.
- Tags in the form: `components/TagsField.tsx` is a multi-value freeSolo Autocomplete that renders one hidden `tags` input per tag, so the builders read them with `FormData.getAll("tags")`; `TransactionSeed.tags` carries them through duplicate, template and "Add another". Tag colours come from `lib/tags.ts` (`tagAccent`); show them with `TagChip` / `TagChips`. The tag filter is the URL params `tag_ids` (an array) and `tag_match`, threaded like `category_id`: `lib/transaction-filters.ts`, `TransactionFilters` (the `TagFilter` multi-select with a "Must have all of them" switch, over the full tag list), the page's search schema, `server/transactions.ts`, and the export button and route, which repeat `tag_ids` and forward them as repeated `tag_id`. `apiRequest` takes an array query value and repeats the key.
- Vendor defaults in the form (`transaction-form/useVendorDefaults.ts`): picking or typing a known vendor fills the category and tags that are still empty, never what was already typed, and only for a real user action (`NamePickerField`'s `onValueChange(value, fromUser)` is false when the field sets its own starting value, so opening an edit, a duplicate or a template pre-fills nothing). The uncontrolled category and tag fields are refilled by remounting them with a new `key` and default; the rule itself is the pure `defaultsToFill`.
- Row selection (`lib/selection.ts`, `components/SelectionBar.tsx`): `useSelection(ids)` keeps a selection that belongs to the rows on screen and starts empty again whenever they change (page, filter, deletion), so a bulk action never reaches a row you can no longer see. Pages wrap their table in a list component (`TransactionList` in the Transactions route, `TrashList` on the Trash page) that owns the selection, the bar and the dialogs, keeping the page itself small for react-doctor. Dialogs keep the ids they were opened with. `lib/bulk-message.ts` turns a `BulkResult` into the toast ("Updated 8 transactions. 2 skipped: …"). Once every row on the page is ticked and more match, `SelectAllMatching` (in the bar's `extra` slot) offers "Select all N matching": it fetches the ids (`listMatchingIdsFn`, `listTrashIdsFn`) and `selection.selectAll` holds them (`wide`), still ending as soon as the rows on screen change. The bulk server functions take up to `MAX_SELECT_ALL` ids and send them to the API in batches of 500 (`bulkCall`), saved batch by batch and reported as one result.
- Passwords in the web: Settings has `PasswordCard` and `ChangePasswordDialog` (current password, the new one twice checked in the browser, and a `SecondFactorField` when two-factor is on; `SecondFactorField` is the code input with the recovery-code toggle that `TwoFactorConfirmDialog` shares). After a change the toast says the other devices were signed out.
- Sessions in the web: the cookie holds the API's session token (not the user's password or a JWT) and lasts 90 days from its last renewal (`COOKIE_SECONDS` in `utils/session.ts`), longer than the API's 30, so the API decides when a sign-in really ends and answers 401. `apiRequest` re-issues the cookie at most every six hours while it is in use (`renewSession`), so an active device never loses it, and passes the visitor's address (`X-Forwarded-For`) and browser (`User-Agent`) to the API, because the API only sees the web server. `logoutFn` ends the session on the API before clearing the cookie. Settings has `SessionsCard` ("Where you are signed in": `describeDevice` in `lib/user-agent.ts` turns the User-Agent into "Firefox on Linux", `formatAgo` says "5 minutes ago", a Sign out button on each other device, "Sign out all other devices"). Everyone is signed out once when this ships, because the old tokens are gone.
- Two-factor in the web: `loginFn` keeps the challenge in its own short-lived encrypted cookie (`getChallengeSession`, `maalu_2fa`, five minutes), so the browser never holds it, and answers `{twoFactor: true}`; the login page then shows `TwoFactorStep` (`verifyTwoFactorFn`, a recovery-code toggle, back to the password; a dead challenge returns to the password with a message). Settings has `TwoFactorSettings` (a card with On/Off, "Set up", "New recovery codes", "Turn off") and three dialogs: `TwoFactorSetupDialog` (QR plus the key to type by hand, confirm with a code), `TwoFactorConfirmDialog` (password and a code or recovery code, for turning off and for new codes) and `RecoveryCodesDialog` (shown once, copy and download, only the button or Escape closes it).
- Start from a template is a setting (`users.start_from_template`): when it is off the Transactions loader passes the form an empty template list, and the form hides the picker when there are none.
- Refunds in the web: an expense row has a Refund button (`canRefund` in `lib/refund.ts`) that opens `RefundDialog` (through `RefundDialogHost` and `useRefundDialog`, which also sends the Edit of a refund there instead of the big form): the amount (up to what is left), or for a purchase with items a tick-and-amount per item (`RefundItems`), the date and time, the account in the purchase's currency, the rate (starting as the purchase's) and a note. Refund rows carry a green "Refund" tag and an undo tile, with no Duplicate; the purchase shows "Refunded MVR 30.00" or "Fully refunded". The totals card says "after refunds" when there were some, and the monthly chart draws a month below zero as zero (its table still shows the figure).
- Planned transactions in the web: the form's "Planned" switch (`useFormFields`) turns on by itself when the date is in the future and follows the date until you set it yourself (an existing transaction keeps what it has); a planned expense gets no budget warning, since it counts toward nothing yet. The Transactions page loads `listUpcomingFn()` and shows an `UpcomingCard` above the list (due date label from `lib/planned.ts`, overdue in red, one-click "Mark as paid" through `MarkPaidDialog` with the real date and amount). `lib/tx-display.ts` holds the title helpers the table, cards and upcoming list share.
- Budget warnings: after an expense is saved, `components/transaction-form/budget-warning.ts` refetches the budget for the transaction's date and, if a limit covering its categories is close or over, appends one sentence to the save message (`useNotify` severity `warning`). The Transactions page shows a `BudgetAlert` strip while any limit needs attention. Both stay quiet for past periods.
- Sign-in and register pages share `components/AuthLayout.tsx`: the form on one side and a flush coloured panel on the other (a short banner on a phone). The panel is `components/GradientASCII.tsx`, a WebGL2 gradient (deep blue to near-white, from the theme's primary and info colours) redrawn in text characters that scramble under the pointer and on click. Its shape fades to nothing on one side, over the page background, so the panel blends into the form: side by side it is turned a quarter (`rotate`) so the empty, white side faces the form on the right, and as a phone banner it faces down at the form. It stands still for reduced motion and pauses when off screen; where WebGL2 is missing it falls back to a static CSS mesh with SVG noise. `GradientASCII` is adapted from React Bits (MIT + Commons Clause, see the header comment): fine as part of the app, but it is not Apache-2.0 code, so keep that notice and don't repackage it on its own. Colours are any CSS colour (`var(--mui-palette-*)` works, resolved by `lib/css-color.ts` and re-read when the colour mode changes). The headline stays in the left 42%, over the blue. On a phone the form is centred vertically and the banner takes the room above it. The pages' own fonts are constants at the top of `AuthLayout.tsx`: `PAGE_FONT` (the form), `GLYPH_FONT` (the gradient's characters) and `SCRIPT_FONT` (Homemade Apple, `src/assets/HomemadeApple-Regular.ttf`, declared in `styles/m3.css`), which is used for the app name (`components/Brand.tsx`, so the sidebar, the phone header and the pages' panel) and the tagline on the coloured panel, and nowhere else. The rest of the app keeps the theme's font. White text keeps its contrast over it in light and dark mode. `subtitle` is optional.
- Tables: every list goes through `components/ResponsiveTable.tsx`. In table mode both the wide table and the narrow card list draw each row as its own rounded bar (`ROW_FILL`, one tonal step above the card, so it shows in light mode too): the wide table does it with `borderSpacing`, tinted cells and the row's corners on its first and last cell, so hover and selection tint the cells (`.Mui-selected`) rather than the row. Don't add row borders or row backgrounds in a page's `renderRow`.
- Navigation: `lib/nav.ts` lists every destination (`NAV_ITEMS`, grouped). Wide screens show them all in the sidebar (`SideNav`); narrow screens show the four marked `bottom` (Dashboard, Transactions, Accounts, Budget) in the bottom bar plus **More** (`NavButton` in `NavItem.tsx`), which opens a bottom sheet (`MoreSheet` in `BottomNav.tsx`) with every destination grouped like the sidebar, as a grid of the same items; picking one closes it, and More shows as the current tab on any page outside the four (`inBottomBar`). Badges (Pending's count) show on the item in the sheet and add up on More. So a new destination needs nothing for phones: it appears in the sheet; give it `bottom` only if it should replace one of the four. The sheet slides on MUI's plain curve, not the `linear()` spring, which Safari animates badly.
- Dashboard (`/dashboard`, the home page) and charts: the charts are hand-drawn, not a library (`components/charts/`): SVG only for lines and washes with non-scaling strokes, everything with text (axis labels, dots, tooltips) in HTML on top. They follow the dataviz rules: 2px lines, bars at most 24px with a 4px rounded tip, hairline solid grid, a legend for two or more series, a hover/focus readout, and a "show as a table" toggle on every chart card. Chart colours are `--chart-income`, `--chart-expense` and `--chart-line` (`CHART_LIGHT` / `CHART_DARK` in `lib/m3.ts`), validated with the palette checker; dark mode has its own steps. Income and expense are green and orange, not red, because red/green fail for deutan colour vision. Net worth comes from `GET /stats/balance-trend` (computed from transactions on demand, each account at its current manual rate); income/expense per month from `GET /stats/monthly`.
- **Docs** (`/docs` and `/docs/$slug`, `routes/_protected/docs.index.tsx` and `docs.$slug.tsx`, sidebar group Help, icon `article`) is the in-app guide to what each feature is and how to use it. **A guide is data, not a page**: `lib/docs/<name>.ts` exports a `Doc` (`slug`, `title`, `summary`, `symbol`, `accent`, `where` links and `blocks`), `lib/docs/index.ts` lists it in `DOCS`, and the index and article pages draw it. Blocks are `h2` (with an `id`, which feeds the "On this page" list), `p`, `steps` (numbered), `list`, `callout` (tip, note or warning), `example` (a worked table) and `faq`; text may use `**bold**` for the name of something on screen and `[label](/page)` for a link that stays inside the app (`inlineSegments`; `DocBlocks` renders it with `RouterLink`, and **a test fails when a link points at a page that does not exist**, `pageExists`: every sidebar destination, `/settings`, `/profile`, `/notifications` and the guides themselves), and nothing else. **Link the first mention of a page in each section** so the guides are easy to move around in. `DocBlocks` is the one renderer, so every guide looks the same. A test checks every guide: unique slugs, unique heading ids, balanced `**`, links to real pages, and unique block and item text (it is the React key, since react-doctor bans index keys). **To add a guide**: write the file, import it into `DOCS`, and keep it in step with the feature (a guide that is wrong is worse than none). Guides so far, in the index order (setting up, organising, bills, planning, then reports and the rest): Accounts, cards and groups; An account's page; Import a bank statement; Refunds, transfers and corrections; Categories; Tags; Groups; Subscriptions and recurring bills; Bills that change each month; Budget and spending limits; Savings goals; Month plan and available to spend; Split your salary; Reports (Compare, Trends, Net worth, needs and wants); Places and the map; Backups and restoring. Not yet written: Vendors, Templates, Trash, and a guide for Settings' security cards (two-factor, sessions, password). Each file names the CLAUDE.md paragraphs it must stay in step with. **Search** (`searchDocs` in `lib/docs/search.ts`, the box on the Docs page, `?q=` in the URL): a guide matches when it contains every word typed, in any order, ignoring case and the `**`/link markup, across its title, summary and every block; title matches rank first, then the summary, then how often the body mentions the words; a match found only in the body shows its section and a passage, and the card opens the guide at that section (`#id`). **Screenshots** are an `image` block (`src` = `/docs/<name>.webp`, `alt`, real `width` and `height` so the page does not jump, optional `caption`; `Shot` in `DocBlocks` draws it lazy and outlined) and live in `apps/web/public/docs/`, which the build copies into the image. **They are made, not hand-captured**: `just docs-shots` (`e2e/docs-shots.spec.ts`, which `playwright.config.ts` leaves out of every other run through `DOCS_SHOTS`) seeds a user (`shots@example.com`, the seed's made-up data, `app.seed --email`) in the e2e database, adds a credit card with a statement through the API, signs in, and for each screen clips the page's content (not the sidebar, and below the banner, `BANNER`) to at most 900 px tall, adds `PAD` (28 px) of the page's own background all round so rounded corners are not cut off (a shot cut at the maximum height also fades out at the bottom), and saves a **WebP converted by Chromium's own canvas** (no image library installed), printing each file's size so the `width`/`height` of its block can be copied; they come to 18 to 50 KB each. **Light mode only.** One so far (`compare` in Reports, a whole page that depends on loader data); to add one, add a `shoot(...)` to the spec, run `just docs-shots`, and put an image block in the guide. A test checks every block's file exists, is a `.webp` under 150 KB, has a real alt, and is used once; the search reads alt and caption. Re-shoot only when a screen a guide shows has really changed, since each new version stays in git history. **Live examples** are the alternative to a screenshot for a self-contained piece of the app: a `demo` block (`id`, `title`, optional `caption`) draws the **real component** with made-up data from `lib/docs/demo-data.ts`, so it can never go stale, follows dark mode and the theme, reflows on a phone and is real text. It sits in a dashed frame labelled "Example with made-up data", inside an `inert` box with `pointer-events: none`, so nothing in it can be focused or pressed and it sends nothing. An id lives in `lib/docs/demo-ids.ts` (`DEMO_IDS`) and its component in `components/docs/Demos.tsx` (a `Record<DemoId, ...>`, so the type requires both); the component must be presentational (props only, no loader, server function or app shell). Four so far, all replacing screenshots: `card-statement` (`CardStatementPanel`, Accounts guide), `plan-agenda` (`PlanAgenda` fed by `planDays(planDemo)` in the card the page draws it in, Month plan guide), `budget-limits` (`BudgetSummary` and four `BudgetLineCard`s, Budget guide) and `salary-rules` (the whole `SalaryRulesCard`, whose dialogs only mount when opened, Salary guide). The fixtures are typed against the generated API types, so a schema change breaks them at compile time instead of leaving a stale example. Prefer a demo for a piece built from props and a screenshot only for a whole page. **Each page links to its guides**: `PageHeader` shows a frosted pill "Guide: <title>" for every guide that explains the page (`GuideLinks`, `useRouterState` for the path), taken from `GUIDES_FOR_PAGE` in `lib/docs/for-page.ts` (`/accounts` Accounts, cards and groups; `/accounts/<id>` An account's page through `guidesForPath`; `/transactions` Refunds, transfers and corrections; `/subscriptions` Subscriptions and Bills that change; `/budget` Budget and Savings goals; `/plan` Month plan; `/pending` Split your salary; `/import`; `/compare`, `/trends` and `/net-worth` Reports; `/categories`, `/tags`, `/groups` and `/places` their own; `/settings` Split your salary and Backups and restoring). It needs no change to a page: add a route to the map, and a test checks every key is a real page and every slug a real guide. A page with no entry (vendors, tags, settings...) shows none, and the guides themselves never do. `docs-shots` finds a page's banner by its gradient (not a fixed height), so a banner that grows a row does not spoil a shot. Not built: dark-mode screenshots, guides for Vendors, Templates, Trash and Settings' security cards, a link from each Settings card to its guide.
- **Shape morph (a universal rule):** anything that can be hovered or focused (cards, pills, chips, nav items, buttons, the search bar) rests at one corner token and springs to the next, less rounded one under the pointer or focus. Use `morph("xl")` (cards, 28px to 16px) or `morph("24px", "md")` (a pill, 24px to 12px) from `lib/shape.ts` instead of writing a radius by hand; MUI buttons, icon buttons and `Card` already do it through `theme.ts`. A pill rests at half its height, not `full` (999px), or the corners would not start moving until the spring's last frames. If the element sets its own `transition`, start it with `MORPH_TRANSITION`.
- Imports use the `#/` alias for `src/`. `routeTree.gen.ts` is generated, so don't edit it.
- New `@mui/icons-material` icons must be added to `optimizeDeps.include` in `vite.config.ts`. Without that, dev mode re-optimises mid-session and throws a duplicate-React "Invalid hook call".
- Style: oxfmt (tabs, double quotes) and oxlint. react-doctor is a gate, so recent work memoises table rows/components and splits large components (see `components/transaction-form/`). Theme colours come from CSS variables and theme tokens, not hard-coded values. The look is Material 3 Expressive (MUI default blue primary): colour roles in `lib/m3.ts`, springs, the `--shape-*` corner scale in `styles/m3.css`, wired up in `theme.ts`. Ripples are MUI's own, on everywhere, and there is no custom focus ring: keyboard focus is the pulsing ripple (nav items opt in with `focusRipple` and also take their hover tint), links keep the browser's outline. Colour a nav ripple through `.MuiTouchRipple-root .MuiTouchRipple-child` (anything less specific loses to MUI's own rule). Text fields are outlined (`MuiTextField` default variant in `theme.ts`, 4px corners, hairline border, 2px primary ring on focus); the search bar (`SearchField`) is the one filled field. Use the shape variables, not pixel radii; use `var(--md-sys-color-*)` or `color-mix` for anything that must follow light/dark (not `theme.palette`, which is always the light scheme). Icons that animate use `components/Symbol`, whose bundled font is a subset, so check a new icon name renders.
