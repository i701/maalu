# CLAUDE.md (iOS)

## iOS app (`apps/ios`)

SwiftUI, iOS 26 and later, Swift 6 language mode. The Xcode project is **generated** by XcodeGen from `apps/ios/project.yml` and not committed: `just ios-project` makes it, `just test-ios` runs the unit tests on a simulator, and a new file under `Maalu/` is picked up by regenerating. `buildServer.json` and `.compile` (made by `xcode-build-server` so Zed's language server sees the project) are machine-specific and ignored.

**Always use the `swiftui-pro` skill (`~/.claude/skills/swiftui-pro`, from twostraws/swiftui-agent-skill) when writing or changing iOS code, and follow its SKILL.md and the reference files that apply** (api, views, data, navigation, swift, design, accessibility, localization). The rules that bite most here:
- **One type per file** (struct, class, enum), in a folder by feature. No `some View` computed properties or methods to split a body: extract a `View` struct in its own file. Button actions and anything beyond layout go in methods, never inline in `body` or `task`.
- **Logic lives in `@Observable @MainActor` models** (state owned with a private `@State`, passed with `@Environment` or `@Bindable`), so it can be unit tested. No `ObservableObject`. Identity comes from the element (`Identifiable`), not `\.self` or an index.
- Modern API only: `foregroundStyle`, `Tab`, `navigationDestination(for:)` (never `NavigationLink(destination:)`), the two-parameter `onChange`, `Button("Label", systemImage:, action:)` so VoiceOver has text, `ContentUnavailableView` for empty and no-results states, no `UIKit`, no `DispatchQueue`, no force unwraps or `as!`, no `String(format:)` (use `FormatStyle`), no `Text` built with `+`. Filter typed text with `localizedStandardContains`. Money is a `Decimal` parsed from the API's string and formatted with `.currency(code:)`, never a `Double`.
- **Number fields use `DecimalField` (`Shared/`), not `TextField(value:format:)`**: the latter writes its value only when editing ends, so Save or Apply tapped from the keypad misses it. Two-way text and value syncing needs care (a value-to-text rewrite while typing resets the field), which is why `DecimalField` only rewrites the text when the value changed from outside.
- **A form that saves shows it is waiting**: its confirm button is `SaveButton` (`Shared/`; a spinner in its place while the request is out, the button again on success or failure), and the form takes `.saving(isSaving)` before its `.navigationTitle` (nothing can be changed and the sheet cannot be swiped away) with `.disabled(isSaving)` on its Cancel and any other toolbar action. No spinner laid over the form.
- **A row with a text label and an amount uses `AmountRow` (`Shared/`), not `LabeledContent`**: a long label makes `LabeledContent` drop the value below it, so amounts end up on the right in some rows and underneath in others. `AmountRow` wraps the label and always keeps the amount on the right. It is for short amounts: a long text value (a list of categories) belongs in `LabeledContent`, which wraps it underneath, because `AmountRow` never lets its right side wrap.
- Dynamic Type and system styles, no fixed font sizes, no hard-coded padding or spacing where a default fits; colour is never the only signal (a sign or icon too). New interface text that a model carries is a `LocalizedStringResource`.

**The design pass has started** (inspired by Copilot Money and Apple's Health app, not copied): native SwiftUI, with `Shared/Design/` holding the tokens: `Color.brand` (vivid blue `#437CEF`, the app's tint, for primary actions and key highlights only), `Color.success`, `Radius`, and `.card()` (a white card with a big soft corner and a layered shadow, `Elevation`, level 0 to 6). Screens are cards on `systemGroupedBackground` with colour carried by icons and category tiles, not by large fills. **Keep comments to a minimum**: a doc comment only where the why is not obvious from the name; the amount of comments in the existing files is the ceiling. Write it as a lead developer would: small files, clear names, no dead code, no speculative abstraction.

**Meters follow Bencho's blocks** (MIT, credited in `THIRD_PARTY.md`; the web examples were given as React and redrawn in SwiftUI): the Dashboard's "Where it went" card is the Context meter (`Features/Dashboard/Meter/`): a rolling figure (`numericText`), one bar cut into a piece per category (`SpendingMeterBar`, round at the ends and nearly square between, press or drag to hold a piece), and chips (`SpendingMeterChip`, tap to hold, on a `WrapLayout`). Pieces take their colour by rank from `MeterPalette`, not from the category's own accent, so neighbours always differ; "Other" is grey. The bar is hidden from VoiceOver and the chips carry the name, amount and share. The Dashboard's "Spending by month" card (iOS-only section `spending-trend`, `Features/Dashboard/Trend/`) is Bencho's Traffic block in Swift Charts: `SpendingStack.make` turns `GET /transactions/categories/monthly` into the biggest four expense categories plus "Other" per month (a refund that outweighs a month counts as nothing, so no bar goes below the baseline), drawn as a stacked `BarMark` per month with air between the pieces (`SpendingStackMonth.layers`), 6 or 12 months, press and drag to pick a month, hold a chip to follow one category; the figure and its line (`SpendingStack.reading`) follow what is picked. `MeterChip` and `MeterFigure` are shared with the meter. **The top of the Dashboard is a flat canvas now** (`DashboardCanvas`): Kept this month shows a donut (`DeckDonut`, Swift Charts `SectorMark`, two `DonutPart`s, shares from `KeptSplit`) of income kept against spent with a legend beside it, the layout of a reference analytics screen; no income means no donut. The space right of the legend holds a small bar chart (`DeckMiniBars`, `MiniBar`): the last six months' kept amounts on the Dashboard (current month solid) and what each account type holds on Accounts (biggest solid). Labels are one letter and made unique with zero-width spaces, since Swift Charts wants distinct x values. The Accounts net worth is the same flat section with a donut of assets against liabilities (`AccountsSummarySection`, flat through `deckIsFlat`), no longer a card. the two summaries (`DashboardSection.isInDeck`: Available to spend and Kept this month; neighbouring ones share one canvas, and `DashboardModel.blocks` splits it where another card was arranged between them, so a summary can sit anywhere in the order; net worth is not on the Dashboard, it is on Accounts, and the `balance` id stays in the enum only because it is the web's and is never shown here) are plain text, pills, a bar and a line on the backdrop, one under the other with hairlines, no cards, shadows or pattern: `DeckCardFrame` draws only its content in the card's ink when `deckIsFlat` is set. Header backdrop and accents: `gradientHeader` draws the sky (light) or midnight (dark) `HeaderWash` image fading into the page, and `accentTint` ignores the screen's accent and tints everything the theme blue. The stacked, swipeable deck below (`DashboardDeck`, gesture, blur, springs) is still in the code but not used; `DeckCardFrame`'s card look is still used by the Accounts net worth card. Older description of the deck:

**The top of the Dashboard was a deck** (`Features/Dashboard/Deck/`): Available to spend, Income and spending and Net worth (`DashboardSection.isInDeck`) are compact (about 168pt) gradient cards (`DeckCardFrame`: a pale gradient of the card's own hue, a topography SVG from `Resources/Assets.xcassets` (a template vector image) tinted at 16% (light) or 20% (dark) opacity and full strength along the bottom edge and fading out to nothing by about halfway up the card, so the title and figure sit on a clean background, the fade sized to the card, as an overlay so it never changes the card's size, and all text, bars and the line in that hue, and frosted pills (`DeckPill`, `ultraThinMaterial`, whitened over in light mode because the bare material reads grey on a pale card) that blur the pattern behind them; the cards carry the level 2 layered shadow (`Elevation`, drawn as level 1 in dark mode), but only the front card: `Elevation` can be switched off (`isOn`), and the ones behind it (`deckDepth` > 0) have no shadow layers or dark-mode highlight, because those are white shapes and blurred with the card they showed as a white glow, deepened or, in dark mode, lightened: `deckInk`, read by views inside the card) stacked with the next ones rising behind, one step smaller and blurred (`DeckPosition`), in the saved order among themselves; the other sections scroll below as cards. Swipe the front card up and the next one comes forward, swipe down and the previous one does (vertical only, `DashboardDeck`): the card under the finger blurs, fades and shrinks as it is pulled (`DeckPosition`), the card follows the finger with growing resistance (`DeckPosition.resisted`, an exponential limit of 110pt) so it has weight, and on release `flip` animates the front index with a soft spring (`settle`, response 0.55 and damping 0.74, a little overshoot; a drag let go of too soon snaps back on a bouncier `snapBack`), so so every card travels from where it is to its new place and nothing jumps or enters from outside; the stack is not clipped (a straight cut showed as a hard edge mid-swipe) but masked, solid over the stack and fading out across a 70pt margin around it, so a card pulled past the edge dissolves; there are no page dots (they read as a sideways carousel): the stacked edges above the front card are the only cue, and VoiceOver reads "Card 2 of 3" and adjusts with swipe up and down. **A vertical swipe loses to the page's scroll view, so `DashboardView` switches scrolling off while a finger is on the deck (`isDeckHeld`)**: a swipe that starts on the deck flips cards, one that starts anywhere else scrolls. Figures inside deck cards take no taps (`allowsHitTesting(false)`), or the swipe's release opens their full-amount popover. A card hidden in Arrange leaves the deck. **The transaction form is three pages** (`TransactionFormView`, `TransactionFormPage`, `TransactionTypePicker`), after the Copilot Money navigation: a horizontal paging `ScrollView` holds one `Form` per type (Income, Expense, Transfer) side by side, so the neighbouring page is on screen and moves with the finger, and above it is the fixed type bar (not in the form: the first child of a `VStack`, since a `safeAreaInset` let the form scroll up behind it). The pages sit in one container (a `systemGroupedBackground` rounded at the top, clipped, so scrolling content never passes behind the bar) under a shorter backdrop wash (`gradientHeader(height: 320)`) so the bar sits on its pale end. Each page is laid out for its own type, not the draft's: the sections that depend on the type read `\.formType` (`FormType.swift`; `TransactionAccountSection`, `TransactionTypeSection`, `TransactionDetailsSection`, and the page for Details and Items), and every page edits the same `TransactionFormModel`. The bar is loose labels with one Liquid Glass pill (a plain `.regular` glass capsule drawn as its own layer under the labels, because glass applied to or behind a label blurs its text) that follows `progress`, the scroll offset in pages (`onScrollGeometryChange`): it slides and resizes between the two labels the pages are between, and each label takes its type's colour (`ChipColors`, green, red or blue) as the pill reaches it. A tap on a label scrolls to that page. `scrollPosition(id:)` tracks the page in view and writes `model.draft.type` once the form is positioned; the pages are first scrolled to the draft's type with a `ScrollViewReader` after a short wait (`isPositioned`; the scroll view first reports its first page, which must not overwrite the type), and a type set from outside (a template) scrolls the pages to it. The form's own type section is only the amount, a big figure (`BigAmountField`: the currency in muted text over a `largeTitle` `DecimalField`, like the transfer slabs), and the account is a row showing its name, currency, number and balance (`Account.numberAndBalance`) that opens `AccountChoiceSheet`, a list whose rows show the same under each name. **Save is a floating Liquid Glass button** (`FloatingSaveButton`, `glassProminent`, 46pt, inset 28pt each side, over the bottom of the container) and not in the toolbar, so the title is centred between Cancel and the template button. The form fades into blur under it and at the container's top edge with `EdgeBlur` (a material masked by a gradient, 110pt at the bottom, 36pt at the top, drawn as overlays inside the container's clip), and each page has content margins so its first and last rows clear them. The container runs to the screen's bottom edge: `ignoresSafeArea(.container, edges: .bottom)` is on the `VStack` (on the scroll view inside it, it did nothing), the home indicator's height is measured outside it (`bottomInset`, from the `NavigationStack`) and added to the Save button's padding, the bottom blur and the pages' bottom margin. SwiftUI's own `scrollEdgeEffectStyle`/`safeAreaBar` did not blur here: it only reaches the scroll view the bar sits on, which would be the horizontal pages, not the vertical forms inside them.

**The transfer form is Bencho's Asset swap** (`Features/Transactions/Form/Transfer/`): for the Transfer type `TransactionAccountSection` shows `TransferSlabs` in place of the From and To pickers and the Amount field. Two slabs, "From" (the amount typed, `draft.amount`) over "To" (the same amount shown, or `draft.toAmount` typed when the accounts are in two currencies, `needsToAmount`), each with an account chip, and, once an account is chosen, its number and balance in muted text at the top right of the slab and under its name in the list (`Account.numberAndBalance`). Pressing a chip grows that slab over the whole block into the account list (`TransferAccountList`) and fades the other; picking shrinks it back. **The size is driven by an `Animatable` modifier (`TransferSlabGrowth`), not a plain `.frame` change: a Form row did not animate a change of frame or offset (found by recording the simulator and reading the frames), only render-level properties like opacity.** Open and close are explicit `withAnimation` springs (0.38s and 0.3s). The slab's content is clipped to its current height (a list taller than the slab spilled out over the other slab while it grew), and the face and the list fade one after the other, never together (`isOpen` animations on the face, an asymmetric transition on the list). The arrow on the seam (`TransferFlipButton`) turns half a turn each press, always the same way, and swaps the accounts and, in two currencies, the amounts. The rules are on `TransactionDraft` (`reverseTransfer`, `chooseTransferAccount`: an account already on the other side trades places with the one it replaces) and tested. Not done: the web's fee and price maths between the two slabs (the app has no fee; a cross-currency amount is typed). Next in the same direction: nothing planned.

**The sign-in screen** (`Features/Login/`) is a `ScrollView` on `gradientHeader` (the sky or midnight wash): the Maalu mark (`AppMark`, `maalu.svg` from the app icon, in the `MaaluMark` image set as a template so it takes navy in light mode and pale blue in dark), the email and password on one `.card()` (`LoginFieldsCard`), and a `glassProminent` brand button like the transaction form's Save (46pt). **The second step is Bencho's One-time code** (`Features/Login/Otp/`): `OtpField` is six cells drawn by `OtpCells` plus one invisible real `TextField` (`.oneTimeCode`, number pad) over them, so paste, autofill and backspace stay the system's; a full row checks the code at once (`onComplete`). `OtpCells` is `Animatable` in `merge` and `shake`: its `Canvas` blurs the cells and runs `alphaThreshold` so they fuse; a right code (`LoginModel.isVerified`, which holds `session.signedIn` back about 1.1s so the animation plays) slides the cells together while a capsule grows and says "Verified"; a wrong one (`codeFailures` goes up) shivers the row, lets the digits fall out right to left and clears the code; while the server checks, a wave of breath goes through the cells. A recovery code is a plain text field with the Verify button. Not checked: the success fuse against a real server (only the wrong-code path was run in the simulator), large text sizes, dark mode.

The wire format is the API's: types are hand-written `Decodable` structs with `convertFromSnakeCase` for now (generating them from `apps/web/openapi.json` is the next step), money stays a string on the wire, the session token is in the Keychain, and the server address is asked for (`GET /api/v1/server` says whether it is a Maalu server). iOS is the web's and Android's third client: a screen is built to the same rules as theirs, and `parity/features.json` is updated with it.
