# Web features

How the web app does particular things (`apps/web/src`). The architecture rules are in the root CLAUDE.md.

- Transaction form entry speed: the form starts from a `TransactionSeed` (`components/transaction-form/request.ts`), made from an edited transaction, a duplicate (`seedFromTransaction`, the old rate dropped so the market rate is suggested; editing keeps the saved rate, `initialValues` in `schema.ts`), a template (`seedFromTemplate`) or what was just saved (`seedAfterSave`, which keeps account, category, vendor and method and clears the amount and note). Every field is a react-hook-form value: `transaction-form/schema.ts` holds the fields, the cross-field rules (`transactionSchema`: two different accounts for a transfer, what arrived across currencies, an amount and category unless the items table is on, a rate for a foreign currency) and the starting values (`initialValues`); `useFormFields` owns `useForm` and the rules that tie fields together (a card sets its account and method, an account suggests a method, a new currency starts its rate fresh, a future date turns on Planned until you set it). The request builders in `request.ts` take the checked values plus what they point at (`State`). The pickers that only read a starting value (category, vendor, tags, currency) remount when `round` changes (the form refilled from a seed). "Add another" keeps the dialog open after a *new* transaction, "Save as template" reads the form into a template, and the Transactions page has a Duplicate button on every row. Child components take a `seed`, never the `transaction`, so only `request.ts` and the form itself know whether it is an edit.
- Category colours in the web: `lib/categories.ts` (`categoryAccent`, `categoryPath`, `parentChoices`), `CategoryDot` beside names (Categories page, transaction subtitle, `CategoryBreakdown` bars), `ColorSwatches` and a parent select in `CategoryForm` (colour left empty on a new category = automatic). The Categories page indents sub-categories under their parent.
- Tags in the form: `components/TagsField.tsx` is a multi-value freeSolo Autocomplete that reports the list through `onChange` (a form wraps it in a `Controller`); `TransactionSeed.tags` carries them through duplicate, template and "Add another". Tag colours come from `lib/tags.ts` (`tagAccent`); show them with `TagChip` / `TagChips`. The tag filter is the URL params `tag_ids` (an array) and `tag_match`, threaded like `category_id`: `lib/transaction-filters.ts`, `TransactionFilters` (the `TagFilter` multi-select with a "Must have all of them" switch, over the full tag list), the page's search schema, `server/transactions.ts`, and the export button and route, which repeat `tag_ids` and forward them as repeated `tag_id`. `apiRequest` takes an array query value and repeats the key.
- Vendor defaults in the form (`transaction-form/useVendorDefaults.ts`): picking or typing a known vendor fills the category and tags that are still empty, never what was already typed, and only for a real user action (`NamePickerField`'s `onValueChange(value, fromUser)` is false when the field sets its own starting value, so opening an edit, a duplicate or a template pre-fills nothing). It sets the form's category and tags and remounts those pickers with a new `key` so they show it; the rule itself is the pure `defaultsToFill`.
- Row selection (`lib/selection.ts`, `components/SelectionBar.tsx`): `useSelection(ids)` keeps a selection that belongs to the rows on screen and starts empty again whenever they change (page, filter, deletion), so a bulk action never reaches a row you can no longer see. Pages wrap their table in a list component (`TransactionList` in the Transactions route, `TrashList` on the Trash page) that owns the selection, the bar and the dialogs, keeping the page itself small for react-doctor. Dialogs keep the ids they were opened with. `lib/bulk-message.ts` turns a `BulkResult` into the toast ("Updated 8 transactions. 2 skipped: …"). Once every row on the page is ticked and more match, `SelectAllMatching` (in the bar's `extra` slot) offers "Select all N matching": it fetches the ids (`listMatchingIdsFn`, `listTrashIdsFn`) and `selection.selectAll` holds them (`wide`), still ending as soon as the rows on screen change. The bulk server functions take up to `MAX_SELECT_ALL` ids and send them to the API in batches of 500 (`bulkCall`), saved batch by batch and reported as one result.
- Passwords in the web: Settings has `PasswordCard` and `ChangePasswordDialog` (current password, the new one twice checked in the browser, and a `SecondFactorField` when two-factor is on; `SecondFactorField` is the code input with the recovery-code toggle that `TwoFactorConfirmDialog` shares). After a change the toast says the other devices were signed out.
- Sessions in the web: the cookie holds the API's session token (not the user's password or a JWT) and lasts 90 days from its last renewal (`COOKIE_SECONDS` in `utils/session.ts`), longer than the API's 30, so the API decides when a sign-in really ends and answers 401. `apiRequest` re-issues the cookie at most every six hours while it is in use (`renewSession`), so an active device never loses it, and passes the visitor's address (`X-Forwarded-For`) and browser (`User-Agent`) to the API, because the API only sees the web server. `logoutFn` ends the session on the API before clearing the cookie. Settings has `SessionsCard` ("Where you are signed in": `describeDevice` in `lib/user-agent.ts` turns the User-Agent into "Firefox on Linux", `formatAgo` says "5 minutes ago", a Sign out button on each other device, "Sign out all other devices"). Everyone is signed out once when this ships, because the old tokens are gone.
- Two-factor in the web: `loginFn` keeps the challenge in its own short-lived encrypted cookie (`getChallengeSession`, `maalu_2fa`, five minutes), so the browser never holds it, and answers `{twoFactor: true}`; the login page then shows `TwoFactorStep` (`verifyTwoFactorFn`; the authenticator code goes in `OtpField`, six drawn cells over one invisible input, the web twin of iOS's `Features/Login/Otp`: a full row checks itself, the cells breathe while it is checked, a right code fuses them into a "Verified" capsule for 1.1s before the app opens, a wrong one shivers the row and drains the digits, and the recovery-code toggle swaps in a plain text field with a Verify button, back to the password; a dead challenge returns to the password with a message). Settings has `TwoFactorSettings` (a card with On/Off, "Set up", "New recovery codes", "Turn off") and three dialogs: `TwoFactorSetupDialog` (QR plus the key to type by hand, confirm with a code), `TwoFactorConfirmDialog` (password and a code or recovery code, for turning off and for new codes) and `RecoveryCodesDialog` (shown once, copy and download, only the button or Escape closes it).
- Start from a template is a setting (`users.start_from_template`): when it is off the Transactions loader passes the form an empty template list, and the form hides the picker when there are none. **The picker is a row of chips** (`transaction-form/TemplatePicker.tsx`: a caption, then one `FilterChip` per template in a row that scrolls sideways; the one picked stays marked) at the top of the form, not a select. The Attachments box leaves room under its key buttons (their edge and shadow hang below), and the link entry is spaced from them.
- Refunds in the web: an expense row has a Refund button (`canRefund` in `lib/refund.ts`) that opens `RefundDialog` (through `RefundDialogHost` and `useRefundDialog`, which also sends the Edit of a refund there instead of the big form): the amount (up to what is left), or for a purchase with items a tick-and-amount per item (`RefundItems`), the date and time, the account in the purchase's currency, the rate (starting as the purchase's) and a note. Refund rows carry a green "Refund" tag and an undo tile, with no Duplicate; the purchase shows "Refunded MVR 30.00" or "Fully refunded". The totals card says "after refunds" when there were some, and the monthly chart draws a month below zero as zero (its table still shows the figure).
- Planned transactions in the web: the form's "Planned" switch (`useFormFields`) turns on by itself when the date is in the future and follows the date until you set it yourself (an existing transaction keeps what it has); a planned expense gets no budget warning, since it counts toward nothing yet. The Transactions page loads `listUpcomingFn()` and shows an `UpcomingCard` above the list (due date label from `lib/planned.ts`, overdue in red, one-click "Mark as paid" through `MarkPaidDialog` with the real date and amount). `lib/tx-display.ts` holds the title helpers the table, cards and upcoming list share.
- Budget warnings: after an expense is saved, `components/transaction-form/budget-warning.ts` refetches the budget for the transaction's date and, if a limit covering its categories is close or over, appends one sentence to the save message (`useNotify` severity `warning`). The Transactions page shows a `BudgetAlert` strip while any limit needs attention. Both stay quiet for past periods.
- Sign-in and register pages share `components/AuthLayout.tsx`: two columns on a wide screen, the logo in the left half and the form in the right; on a phone the panel is a banner above the form with the form right under it. The panel (`Wash`) is the **app icon's gradient**, sky blue `#57bee3` falling through `#94dcf1` into the page colour (stops sampled from `Maalu-iOS-Default-1024@1x.png`): **on a wide screen it spans both columns left to right** (`--wash-across`; the form sits on top of it, the wash's content is kept to the left half with `pr: calc(50% + 48px)`), reaching the page colour at about 90% of the width so its last pale blue lands behind the form's fields rather than at the middle, and top to bottom on a phone (`--wash-down`), with fine SVG `feTurbulence` grain laid over it in `soft-light`; dark mode runs a deep sky blue into the page the same way. In the middle of it, as one centred group, sit the **logo** and, on a wide screen, the tagline under it in navy. **`components/Logo.tsx` is the mark from `maalu.svg`** (four rounded bars that read as an "m"; two shapes, each drawn plain and mirrored, the artwork's outer transform folded into each bar's), filled with a navy-to-slate gradient (`#081d48` to `#233c62`, pale blues in dark mode) through CSS variables; with `animate` the bars rise one after another on the spatial spring when it appears and ripple once under the pointer, and it stands still for reduced motion. The old WebGL `GradientASCII` panel and `lib/css-color.ts` were removed with it on 2026-11-13. The handwriting `Brand` (Homemade Apple) is now only the sidebar's and the phone top bar's app name.
- Navigation: `lib/nav.ts` lists every destination (`NAV_ITEMS`, grouped). Wide screens show them all in the sidebar (`SideNav`); **there is no navigation rail: every screen under 900px (phones and tablets alike) gets the bottom bar** (it was a side rail from 600 to 900px until 2026-11-24; the snackbars sit above the bar until the sidebar's breakpoint, `md`); the bottom bar shows the four marked `bottom` (Dashboard, Transactions, Accounts, Budget) in the bottom bar plus **More** (`NavButton` in `NavItem.tsx`), which opens a bottom sheet (`MoreSheet` in `BottomNav.tsx`) with every destination grouped like the sidebar, as a grid of the same items; picking one closes it, and More shows as the current tab on any page outside the four (`inBottomBar`). Badges (Pending's count) show on the item in the sheet and add up on More. So a new destination needs nothing for phones: it appears in the sheet; give it `bottom` only if it should replace one of the four. **Selecting a segment of a toggle group or a filter chip opens a check** (`CHECK_MASK` in `lib/symbols.ts`, a CSS mask in the text colour) on `--spring-spatial-bouncy` (m3.css: damping 0.45, about 20% overshoot, not an M3 token; the check also scales in from 40%), and in an equal-width toggle group the selected segment takes 1.25 shares to the others' 1, so its neighbours give way; a press squashes it to 96%. Segments that hold an icon, and chips with an icon, get no check (the icon fills instead). **The transactions filters update at once**: `patch` and `clearAll` in `routes/_protected/transactions.tsx` run in a `startTransition` that sets a `useOptimistic` copy of the filters before awaiting `navigate` (which settles when the loader does); the chips, the date presets, the tag filter and the Clear all button read that copy, so a chip springs on the click and not when the data arrives, and the copy drops back to the URL's own when the load ends or fails. The account page's `ChipFilter` still uses its own local state. **Progress bars are one component, `components/ProgressBar.tsx`**, in the M3 Expressive style: a fully rounded filled part, a 3px gap, then a rounded track ending in a stop dot, both springing when the value changes; `tick` draws a target line (the 50/30/20 rule) and `role="img"` is for a bar with no live value. **The Money flow Sankey has an Open full screen button** (`SankeyCanvas`, a full-screen dialog: drag to pan, wheel, pinch or the buttons to zoom, arrow keys, + - and 0 from the keyboard; the diagram is drawn at a roomy real size, `roomyHeight`, and `lib/pan-zoom.ts` holds the zoom maths); its node bars are 6px. **Each page takes its nav colour as its accent** (`accentForPath` in `lib/nav.ts`; `RootDocument` in `routes/__root.tsx` sets `data-accent` on `<html>`, not on the page, so portalled dialogs and menus follow). `lib/accent-roles.ts` builds the primary family (primary, container, `inverse-primary`, secondary container, and the MUI `--mui-palette-primary-*` variables with their channels) from the accent's hue at fixed tones, so contrast is the same for every hue (`accent-roles.test.ts` checks it for all eight, both schemes); `theme.ts` emits them as `:root[data-accent=…]` rules (dark after light, and a system-dark one). Slate has little chroma and stays grey. Pages outside the nav keep the sky blue; error, status and chart colours and the navy brand button never change. Not built: a colour spring between pages (the variables would have to be registered with `@property`). **The help line under a switch is always `SwitchHint`** (`components/SwitchHint.tsx`: 4px below the switch, 64px in so it lines up under the label; the M3 skills give no number for this, so it is ours): use it after every `FormSwitch` or switch `FormControlLabel`, not a hand-set `Typography`. **Every dialog has a glow of the page's accent across its top** (`DIALOG_GLOW` in `theme.ts`: an ellipse 110% wide and 150px tall centred on the top edge, `primary-container` fading to transparent, so it follows `data-accent`). **Dialogs and sheets are white (`surface-container-low`) like the cards; their fields stand out by the `outline` border.** **Slow loads (500ms+) on the dashboard, Trends, Compare and Net worth show `PageSkeleton`** (a route's `pendingComponent`; a search change that loads slowly shows it too, quick ones never do). Count badges (Pending on the nav, unread on the bell) are tertiary, not error. Titles take their role's weight (500); 600 and up is for data and the current item. Stat tiles: green and red ones carry meaning, the headline is `tone="primary"`, the rest `neutral`. **Form dialogs wider than `xs` are full screen on phones** (`FormDialog` sets `fullScreen` under 600px; the theme's `paperFullScreen` undoes the card margin, corners and height cap); the `xs` ones stay cards. The sheet slides on MUI's plain curve, not the `linear()` spring, which Safari animates badly.
- **Theme** (`ColorModeToggle`, in the top bar and on the sign-in pages): a menu of System (the default, follows the device), Light and Dark. MUI keeps the choice in `localStorage`, per device, and puts `data-light` / `data-dark` on `<html>`; hand-written CSS must select those.
- **PWA** (installable, with a small service worker; `public/site.webmanifest`, `public/sw.js`, `public/offline.html`, `lib/pwa.ts`, `components/pwa/PwaRegister.tsx` and `InstallCard.tsx`). The manifest (`id`/`scope` `/`, `display: standalone`, plain and **maskable** icons from `public/icon-*.png`, shortcuts to Transactions, Month plan and Accounts) plus the iOS tags and `viewport-fit=cover` in `routes/__root.tsx` make it installable on Android, desktop and iPhone (Share, Add to Home Screen). **The service worker keeps only the app's own static files and never a page, an API answer or a server-function response** (they hold money data and depend on the sign-in, so they always come from the network: nothing private is left in a cache and nothing can show stale figures): built files under `/assets/` are cache-first (their names carry a hash), `/docs/` images and the icons are stale-while-revalidate, the cache is capped at 150 entries, and a page that cannot be reached shows `/offline.html` (a static page with no data). **Offline reading of data is deliberately not built**; it would be a separate decision (what to keep, for whom, how to wipe it on sign-out). A new version **waits until the person taps Reload** (`PwaRegister` shows a snackbar and sends `SKIP_WAITING`, then reloads once on `controllerchange`), so the app never changes mid-entry; a running app checks hourly and when it returns to the foreground. **It registers only in a production build** (`import.meta.env.PROD`), so `just dev` is never served stale files. `startPwa` (called from the root) captures the browser's one-time `beforeinstallprompt` early and `useInstall` (an external store) hands it to the Settings **Install the app** card, which also covers the standalone case and the iOS instructions. The manifest is served by the static handler as `application/octet-stream`, which browsers accept; a route serving it as `application/manifest+json` is the tidy-up if a browser ever objects. **`theme-color` is one tag**: the head merges meta tags by name, so a light and a dark one would leave only the last. Tests: `lib/pwa-manifest.test.ts` (manifest fields and files, the worker's rules) and the `pwa` e2e spec (manifest, registration and activation, nothing private kept, the Settings card). Not built: offline data, push notifications, background sync, a custom install banner outside Settings.
- **The transactions list is quiet, and the detail is a drawer** (`routes/_protected/transactions.tsx`, `components/transactions/`). A row shows four things: a small type tile, the title (`txRowTitle`: the vendor, else the description the user typed, else the category), one muted line (`txRowLine`: the category and the card or payment method; "Transfer" for a transfer) and the amount (tabular figures; income green with +, an expense red with −, a transfer the text colour). A planned row gets a small Planned or Overdue pill (`TxStatusPill`) and nothing else. Tags, chips (subscription, group, refund, stats), the account, the time and the action buttons are **not in the row**: clicking or tapping it (the title is a real button, so the keyboard reaches it; on a phone `MobileCard`'s `onOpen` makes the card the button, replacing the tap-to-expand there) opens `TransactionDrawer`, a bottom sheet on every screen (a grab bar on phones only; centred, at most 800px wide) with the facts (`Fact` rows, left out when empty: date and time, category, account, paid with, vendor, tags, note, items, place, attachments) and the chips under the amount, under a header that holds the title and chips on the left and **the amount, large, on the right** (up to 3.5rem, in `Figure`'s Sora at weight 600, red for spending and green for income via `TxAmount`'s `coloured`), then labelled buttons (`TxActions` in `TxParts.tsx`, all brand-navy keys (contained) except Delete, a plain `color="error"` button; Edit, Refund or Link to a purchase, Split salary, Make subscription, Duplicate, Delete). An action closes the drawer first and then opens its own dialog, and **editing is the existing form dialog**, not fields inside the drawer. The drawer keeps the transaction's id (not the object) so a refetch keeps it fresh, and keeps it while it slides out. **In the table view the list is grouped by day** (`ResponsiveTable`'s `groups` prop: consecutive rows with the same key share a heading, drawn only in the table view, not in the cards grid; `dayHeading`: Today, Yesterday, Tomorrow or the date); the cards view has no headings, so its cards still show the date (`CardsDate`). No daily total: a day can be cut across two pages, so a total would be wrong. Not built: a raw bank description (the API has none), a receipt preview, editing inside the drawer. The e2e specs that used row buttons now open the row first (`openTransaction` in `e2e/helpers.ts`); they have not all been re-run since.
- **Splitting a purchase by item is a table you edit in place** (`components/transaction-form/SplitEditor.tsx`; the math in `lib/splits.ts`, `useSplits`): **the switch has one place, beside Payment method, whether or not the purchase is split** (it used to take the Category cell's place when switched on and sit on its own row below when off, so it jumped). The form's Category field is its own full-width row that collapses away while split (each item has its own); `Reveal` clips and unmounts, so spacing lives inside the content. **While split the dialog widens** (`FormDialog` `maxWidth` `md`, 900px, with `max-width` on the spring so it glides). The items are **one line each** on a wide screen (CSS grid areas: item, qty, price each, category, amount, remove, under column headings; the fields are small with no floating label, their placeholder and `aria-label` naming them: "Item 1", "Quantity of item 1", "Price each of item 1", "Category of item 1" via `CategoryField`/`NamePickerField`'s new `dense`) and fold on a phone to the item and remove button, then quantity, price and amount, then the category, with a hairline between items. A row's amount (and its GST) is worked out beside it, "–" until quantity and price are valid; **a row added with Add item takes the keyboard**; the last row cannot be removed. **The foot is an invoice's**: the GST mode and rate under the items, then Subtotal, GST (rate%) and Total (`TotalLine`; the subtotal is the total less the tax in it, exact decimals), in a block that starts where the form's right-hand column does (the Time field) and ends where the remove buttons do (`calc(50% - 20px)`, `mr` 12px for the table panel's padding). **The category list in a row** (`NamePickerField` `dense`) drops from the narrow cell as a wider popup (`max-content`, 300 to 420px, `bottom-start`, so it starts at the cell's left edge), and in every category picker **a sub-category's parent shows under its name** ("in Food & drink") instead of after it, where a narrow list wrapped the two. Not built: marking the row that has the problem (the message names it in the dialog), Enter to add a row.
- **The transfer form is two slabs** (`components/transaction-form/TransferSlabs.tsx`, used by `TransferFields`; pure rules in `lib/transfer.ts`; iOS's `TransferSlabs`, after Bencho's Asset swap block, MIT): the **From** slab over the **To** slab, each with the account's number and balance, the currency and a big amount, and a pill at the bottom right with the account's name. **Pressing the pill grows that slab over the whole block into the list of accounts** (`role="listbox"`: arrow keys move, Enter picks, **Escape closes the list and not the dialog**, the picked account takes the keyboard when it opens and the pill gets it back); picking closes it. **An account cannot be on both sides: picking the one on the other side swaps them** (`pickTransferEnd`, and the typed amounts trade places between two currencies, `swapTransferAmounts`), the same as the **arrow on the seam** (`swapTransfer`; **a one-way arrow pointing down, From to To, that spins a full turn each press** so it always ends pointing the way the money goes (iOS turns it half a turn; ending up pointing up would say the money flows the other way); **with only one account chosen it moves that account to the other side**, and it is disabled, drawn solid and dim, only while neither is chosen: MUI makes a disabled icon button transparent, which let the seam show through it, and dimming it with `opacity` fades the fill too, so only the arrow's colour dims). The From slab holds `amount` (`name="amount"`, so `focusAmount` and the e2e labels still find it); the To slab shows the same figure, or **between two currencies is a field for what arrived** (`to_amount`, labelled "What arrived", not "Amount received", so a label search for "Amount" finds one field). **The arrow sits in a pocket the two borders curve round**: a shut slab is not a CSS box but an SVG outline (`lib/slab-shape.ts`, `slabPath`; the top slab's bottom edge, the bottom slab's is the same flipped): the straight edge eases into a round bite (`BITE` 26px against the arrow's 20px radius) along a rounded lip (`FILLET` 14px, a circle tangent to both the edge and the bite, worked out with `dx = sqrt((bite + fillet)^2 - (fillet + gap)^2)`), follows the bite round and eases back out, so each border **bulges away from the other round the button** with a gap between, and the stroke is the border (a 1px line inset half a pixel). The outline is drawn in px, so `TransferSlabs` measures the block with a `ResizeObserver` and redraws with its width; an open slab is a plain CSS rounded block (`CORNER` 16px, the same as `--shape-lg`) because it grows over the block and the arrow is hidden. The arrow is a true circle (the theme's icon-button corner morph is switched off for it). Tried and dropped: a `radial-gradient` mask with a ring drawn at the bite, which looked like a hole with a circle round it, not like the border bending. The schema's messages show under the block and a note says to type what arrived. The old From / To `AccountPicker`s are gone for transfers (income and expense still use them). Not built: the slab's press-and-grow spring is CSS (`top`/`height` on the shared spring tokens), not iOS's physical one; Android.
- **The Categories page's month, spend and limits** (`routes/_protected/categories.tsx`): a month picker in the header (`components/MonthPicker.tsx`, the dashboard's own pill, now shared; the URL param is `on`, any day of the month, left out for the current one) drives the table's **Spent** column (`CategorySpent`) and the header's "spent in <month>" and "not sorted" pills, and a **Limit** column with a donut (`LimitRing` on the shared `components/charts/Donut.tsx`, which the dashboard's Kept donut uses too: a thin ring here, `thickness` 9 against the dashboard's 14). A limit covers several categories, so the ring is the limit's figure and every category it covers shows it. Its tooltip names the limit and, when the budget period is not the calendar month beside it (a period that starts mid-month), the period's dates; for a month other than this one the budget is asked for around the 15th, so the period that holds most of that month is used. Colours: `limitColor` in `lib/budget.ts`, each limit a hue in turn with the page's pink first, **by its place among all the budget's limits, so it keeps its hue whichever month is picked** (it shifts only when a limit is added or removed), and red once the limit's status is not ok. Details of the figures: `docs/claude/api/categories-tags-vendors.md`.
- **The dashboard's "Spending by month" card** (`components/dashboard/SpendingTrendCard.tsx`, section id `spending-trend`, the same id iOS uses, no API change): a year of `GET /transactions/categories/monthly` (`getCategoryMonthsFn` with `trendBounds(12, today)`, in the dashboard loader, the page works without it) drawn as the Trends page's stacked columns (`StackedColumns`, the series from `coloredStack` in `lib/trends.ts`, which Trends now shares), **the 4 biggest categories of the span and the rest folded into "Other"**; refunds past a category's spending count as nothing, as in Trends. A **6 / 12 months** switch (`lastMonths` re-ranks the categories over just the span), a headline figure (the span's spending), and **a chip per category with what it came to: pressing one follows it** (the others fade through `StackedColumns`' `highlight`, and the subtitle and figure become that category's); changing the span lets go. Hovering or focusing a column gives its month (a tooltip, the web's version of iOS's press-and-drag), and the table button lists each month's total. The section is left out until there is some spending in the year. It is full width and sits after Cash flow and Budget; a saved order puts it last until moved. `ChartCard` now keeps its `actions` and the table button together at the right. Not built: picking a month to change the figure (iOS does), a legend that follows the table view.
- **Arranging the dashboard**: the dashboard is a list of `Section`s (`id`, `label`, grid `span` of 6, `node`) built in `routes/_protected/dashboard.tsx` and drawn by `components/dashboard/SectionGrid.tsx`; the three money tiles are one section (`metrics`). The tune button in the month pill starts arranging: every card gets a dashed outline (its content stops taking clicks) and a pill with earlier, later and a drag handle (`@dnd-kit`, pointer and keyboard; the arrows are for phones and for anyone who cannot drag). The order is a draft while arranging and is **saved once, on Done**, only on this device (`useSectionOrder` in `lib/dashboard-layout.ts`, `localStorage` key `maalu.dashboard.order`; **Reset** sets the draft to null, saved as an empty list, the default). `orderSections` in `lib/dashboard.ts` applies it to the sections that are on show (Available and Credit usage only exist with data): unknown ids go last, saved ones not on show are skipped, so a card that appears later lands at the end. Cards keep their own width while arranging, but **outside arranging the cards on show fill their rows**: `fillRows` in `lib/dashboard.ts` lays them out the way the grid places them (a card that does not fit starts a new row) and shares a short row's spare columns between its cards (a lone 4-wide card becomes 6, Spending and Budget with the two 4-wide cards hidden become 3 and 3), so hiding cards or a reorder never leaves a hole; full rows are untouched. **Hiding a card**: each card in arranging mode has an eye button (`SectionGrid`; hidden cards stay in the grid, dimmed, so they can come back); the set is a draft saved once on Done, **only on this device** (`localStorage` key `maalu.dashboard.hidden`, `useHiddenSections` in `lib/dashboard-layout.ts`, a `useSyncExternalStore` so the server render shows everything), never to the account, as Android and iOS keep their own. Reset clears it. 
- **Coming up range**: the dashboard's Coming up card and the Transactions page's upcoming strip get it from `listUpcomingWithinSetting(mePromise)` (`server/transactions.ts`): the loader's one `getMeFn()` promise is shared, and its `upcoming_days` goes to `listUpcomingFn({ data: { days } })`, which sends `date_to` of today plus that (overdue ones still lead; 10 if `/users/me` fails). Settings > Coming up (`UpcomingDaysCard`, a 5 to 30 slider saved on release). The Plan page and account pages call it with no argument and list every planned one.
- Dashboard (`/dashboard`, the home page) and charts: the charts are hand-drawn, not a library (`components/charts/`): SVG only for lines and washes with non-scaling strokes, everything with text (axis labels, dots, tooltips) in HTML on top. They follow the dataviz rules: 2px lines, bars at most 24px with a 4px rounded tip, hairline solid grid, a legend for two or more series, a hover/focus readout, and a "show as a table" toggle on every chart card. Chart colours are `--chart-income`, `--chart-expense` and `--chart-line` (`CHART_LIGHT` / `CHART_DARK` in `lib/m3.ts`), validated with the palette checker; dark mode has its own steps. Income and expense are green and orange, not red, because red/green fail for deutan colour vision. Net worth comes from `GET /stats/balance-trend` (computed from transactions on demand, each account at its current manual rate); income/expense per month from `GET /stats/monthly`.

- Account pickers: `components/transaction-form/AccountPicker.tsx` is a type-to-search `Autocomplete` (matches name, group, currency, bank, number) and each option shows the account's balance on the right (`AccountChoice` = `AccountRef` plus an optional `balance`; an archived account kept for editing has none). Account, From and To in the transaction form, "Pay from" in the subscription form, and the import upload and assign-transfer pickers all use it (the old `accountMenuItems` is gone). The dialog is `fullWidth` at the default `sm` width (`FormDialog`'s `fullWidth` prop). The balance is small and secondary, pushed to the right of the option.

- **Figure blur-in**: `components/Figure.tsx` fades each character that changed in out of a blur (keyframes `figure-blur-in` in `styles/m3.css`, effects spring), keyed by place from the end so unchanged digits stay still. The first showing does not animate (`data-live` is set after mount) and reduced motion turns it off. Old characters vanish at once, they do not fade out.

- **Dashboard summary card** (`components/dashboard/SummaryCard.tsx`, the `metrics` section: the id of the old Income/Spent/Saved section, so a saved order keeps its place): one ordinary card, as the flat canvas on iOS, holding Available to spend (the sum in words, Show the working inline from `AvailableWorking.tsx`, Month plan) and Kept this month (spending change against last month, a donut of kept against spent, the last six months as bars). Side by side from `lg`, one under the other below, parted by a hairline. It sorts like every other section. It replaced the old `available` section, the MetricCard tiles and the phone MetricStrip; `lib/deck.ts` has `keptSplit`. Not built: the iOS swipe stack (iOS dropped it too), animated donut.
