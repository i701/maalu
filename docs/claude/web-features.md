# Web features

How the web app does particular things (`apps/web/src`). The architecture rules are in the root CLAUDE.md.

- Transaction form entry speed: the form starts from a `TransactionSeed` (`components/transaction-form/request.ts`), made from an edited transaction, a duplicate (`seedFromTransaction`, the old rate dropped so the market rate is suggested; editing keeps the saved rate, `initialValues` in `schema.ts`), a template (`seedFromTemplate`) or what was just saved (`seedAfterSave`, which keeps account, category, vendor and method and clears the amount and note). Every field is a react-hook-form value: `transaction-form/schema.ts` holds the fields, the cross-field rules (`transactionSchema`: two different accounts for a transfer, what arrived across currencies, an amount and category unless the items table is on, a rate for a foreign currency) and the starting values (`initialValues`); `useFormFields` owns `useForm` and the rules that tie fields together (a card sets its account and method, an account suggests a method, a new currency starts its rate fresh, a future date turns on Planned until you set it). The request builders in `request.ts` take the checked values plus what they point at (`State`). The pickers that only read a starting value (category, vendor, tags, currency) remount when `round` changes (the form refilled from a seed). "Add another" keeps the dialog open after a *new* transaction, "Save as template" reads the form into a template, and the Transactions page has a Duplicate button on every row. Child components take a `seed`, never the `transaction`, so only `request.ts` and the form itself know whether it is an edit.
- Category colours in the web: `lib/categories.ts` (`categoryAccent`, `categoryPath`, `parentChoices`), `CategoryDot` beside names (Categories page, transaction subtitle, `CategoryBreakdown` bars), `ColorSwatches` and a parent select in `CategoryForm` (colour left empty on a new category = automatic). The Categories page indents sub-categories under their parent.
- Tags in the form: `components/TagsField.tsx` is a multi-value freeSolo Autocomplete that reports the list through `onChange` (a form wraps it in a `Controller`); `TransactionSeed.tags` carries them through duplicate, template and "Add another". Tag colours come from `lib/tags.ts` (`tagAccent`); show them with `TagChip` / `TagChips`. The tag filter is the URL params `tag_ids` (an array) and `tag_match`, threaded like `category_id`: `lib/transaction-filters.ts`, `TransactionFilters` (the `TagFilter` multi-select with a "Must have all of them" switch, over the full tag list), the page's search schema, `server/transactions.ts`, and the export button and route, which repeat `tag_ids` and forward them as repeated `tag_id`. `apiRequest` takes an array query value and repeats the key.
- Vendor defaults in the form (`transaction-form/useVendorDefaults.ts`): picking or typing a known vendor fills the category and tags that are still empty, never what was already typed, and only for a real user action (`NamePickerField`'s `onValueChange(value, fromUser)` is false when the field sets its own starting value, so opening an edit, a duplicate or a template pre-fills nothing). It sets the form's category and tags and remounts those pickers with a new `key` so they show it; the rule itself is the pure `defaultsToFill`.
- Row selection (`lib/selection.ts`, `components/SelectionBar.tsx`): `useSelection(ids)` keeps a selection that belongs to the rows on screen and starts empty again whenever they change (page, filter, deletion), so a bulk action never reaches a row you can no longer see. Pages wrap their table in a list component (`TransactionList` in the Transactions route, `TrashList` on the Trash page) that owns the selection, the bar and the dialogs, keeping the page itself small for react-doctor. Dialogs keep the ids they were opened with. `lib/bulk-message.ts` turns a `BulkResult` into the toast ("Updated 8 transactions. 2 skipped: …"). Once every row on the page is ticked and more match, `SelectAllMatching` (in the bar's `extra` slot) offers "Select all N matching": it fetches the ids (`listMatchingIdsFn`, `listTrashIdsFn`) and `selection.selectAll` holds them (`wide`), still ending as soon as the rows on screen change. The bulk server functions take up to `MAX_SELECT_ALL` ids and send them to the API in batches of 500 (`bulkCall`), saved batch by batch and reported as one result.
- Passwords in the web: Settings has `PasswordCard` and `ChangePasswordDialog` (current password, the new one twice checked in the browser, and a `SecondFactorField` when two-factor is on; `SecondFactorField` is the code input with the recovery-code toggle that `TwoFactorConfirmDialog` shares). After a change the toast says the other devices were signed out.
- Sessions in the web: the cookie holds the API's session token (not the user's password or a JWT) and lasts 90 days from its last renewal (`COOKIE_SECONDS` in `utils/session.ts`), longer than the API's 30, so the API decides when a sign-in really ends and answers 401. `apiRequest` re-issues the cookie at most every six hours while it is in use (`renewSession`), so an active device never loses it, and passes the visitor's address (`X-Forwarded-For`) and browser (`User-Agent`) to the API, because the API only sees the web server. `logoutFn` ends the session on the API before clearing the cookie. Settings has `SessionsCard` ("Where you are signed in": `describeDevice` in `lib/user-agent.ts` turns the User-Agent into "Firefox on Linux", `formatAgo` says "5 minutes ago", a Sign out button on each other device, "Sign out all other devices"). Everyone is signed out once when this ships, because the old tokens are gone.
- Two-factor in the web: `loginFn` keeps the challenge in its own short-lived encrypted cookie (`getChallengeSession`, `maalu_2fa`, five minutes), so the browser never holds it, and answers `{twoFactor: true}`; the login page then shows `TwoFactorStep` (`verifyTwoFactorFn`, a recovery-code toggle, back to the password; a dead challenge returns to the password with a message). Settings has `TwoFactorSettings` (a card with On/Off, "Set up", "New recovery codes", "Turn off") and three dialogs: `TwoFactorSetupDialog` (QR plus the key to type by hand, confirm with a code), `TwoFactorConfirmDialog` (password and a code or recovery code, for turning off and for new codes) and `RecoveryCodesDialog` (shown once, copy and download, only the button or Escape closes it).
- Start from a template is a setting (`users.start_from_template`): when it is off the Transactions loader passes the form an empty template list, and the form hides the picker when there are none.
- Refunds in the web: an expense row has a Refund button (`canRefund` in `lib/refund.ts`) that opens `RefundDialog` (through `RefundDialogHost` and `useRefundDialog`, which also sends the Edit of a refund there instead of the big form): the amount (up to what is left), or for a purchase with items a tick-and-amount per item (`RefundItems`), the date and time, the account in the purchase's currency, the rate (starting as the purchase's) and a note. Refund rows carry a green "Refund" tag and an undo tile, with no Duplicate; the purchase shows "Refunded MVR 30.00" or "Fully refunded". The totals card says "after refunds" when there were some, and the monthly chart draws a month below zero as zero (its table still shows the figure).
- Planned transactions in the web: the form's "Planned" switch (`useFormFields`) turns on by itself when the date is in the future and follows the date until you set it yourself (an existing transaction keeps what it has); a planned expense gets no budget warning, since it counts toward nothing yet. The Transactions page loads `listUpcomingFn()` and shows an `UpcomingCard` above the list (due date label from `lib/planned.ts`, overdue in red, one-click "Mark as paid" through `MarkPaidDialog` with the real date and amount). `lib/tx-display.ts` holds the title helpers the table, cards and upcoming list share.
- Budget warnings: after an expense is saved, `components/transaction-form/budget-warning.ts` refetches the budget for the transaction's date and, if a limit covering its categories is close or over, appends one sentence to the save message (`useNotify` severity `warning`). The Transactions page shows a `BudgetAlert` strip while any limit needs attention. Both stay quiet for past periods.
- Sign-in and register pages share `components/AuthLayout.tsx`: two columns on a wide screen, the logo in the left half and the form in the right; on a phone the panel is a banner above the form with the form right under it. The panel (`Wash`) is the **app icon's gradient**, sky blue `#57bee3` falling through `#94dcf1` into the page colour (stops sampled from `Maalu-iOS-Default-1024@1x.png`): **on a wide screen it spans both columns left to right** (`--wash-across`; the form sits on top of it, the wash's content is kept to the left half with `pr: calc(50% + 48px)`), reaching the page colour at about 90% of the width so its last pale blue lands behind the form's fields rather than at the middle, and top to bottom on a phone (`--wash-down`), with fine SVG `feTurbulence` grain laid over it in `soft-light`; dark mode runs a deep sky blue into the page the same way. In the middle of it, as one centred group, sit the **logo** and, on a wide screen, the tagline under it in navy. **`components/Logo.tsx` is the mark from `maalu.svg`** (four rounded bars that read as an "m"; two shapes, each drawn plain and mirrored, the artwork's outer transform folded into each bar's), filled with a navy-to-slate gradient (`#081d48` to `#233c62`, pale blues in dark mode) through CSS variables; with `animate` the bars rise one after another on the spatial spring when it appears and ripple once under the pointer, and it stands still for reduced motion. The old WebGL `GradientASCII` panel and `lib/css-color.ts` were removed with it on 2026-11-13. The handwriting `Brand` (Homemade Apple) is now only the sidebar's and the phone top bar's app name.
- Navigation: `lib/nav.ts` lists every destination (`NAV_ITEMS`, grouped). Wide screens show them all in the sidebar (`SideNav`); **medium screens (600 to 900px) show the same four plus More as a navigation rail** (`BottomNav` stood on end: `RAIL_WIDTH` 80px down the left edge below the top bar; `AppShell` pads the page by it, and the snackbars sit at the bottom from 600px up); phones (under 600px) show the four marked `bottom` (Dashboard, Transactions, Accounts, Budget) in the bottom bar plus **More** (`NavButton` in `NavItem.tsx`), which opens a bottom sheet (`MoreSheet` in `BottomNav.tsx`) with every destination grouped like the sidebar, as a grid of the same items; picking one closes it, and More shows as the current tab on any page outside the four (`inBottomBar`). Badges (Pending's count) show on the item in the sheet and add up on More. So a new destination needs nothing for phones: it appears in the sheet; give it `bottom` only if it should replace one of the four. **Selecting a segment of a toggle group or a filter chip opens a check** (`CHECK_MASK` in `lib/symbols.ts`, a CSS mask in the text colour) on `--spring-spatial-bouncy` (m3.css: damping 0.45, about 20% overshoot, not an M3 token; the check also scales in from 40%), and in an equal-width toggle group the selected segment takes 1.25 shares to the others' 1, so its neighbours give way; a press squashes it to 96%. Segments that hold an icon, and chips with an icon, get no check (the icon fills instead). **The transactions filters update at once**: `patch` and `clearAll` in `routes/_protected/transactions.tsx` run in a `startTransition` that sets a `useOptimistic` copy of the filters before awaiting `navigate` (which settles when the loader does); the chips, the date presets, the tag filter and the Clear all button read that copy, so a chip springs on the click and not when the data arrives, and the copy drops back to the URL's own when the load ends or fails. The account page's `ChipFilter` still uses its own local state. **Progress bars are one component, `components/ProgressBar.tsx`**, in the M3 Expressive style: a fully rounded filled part, a 3px gap, then a rounded track ending in a stop dot, both springing when the value changes; `tick` draws a target line (the 50/30/20 rule) and `role="img"` is for a bar with no live value. **The Money flow Sankey has an Open full screen button** (`SankeyCanvas`, a full-screen dialog: drag to pan, wheel, pinch or the buttons to zoom, arrow keys, + - and 0 from the keyboard; the diagram is drawn at a roomy real size, `roomyHeight`, and `lib/pan-zoom.ts` holds the zoom maths); its node bars are 6px. **Each page takes its nav colour as its accent** (`accentForPath` in `lib/nav.ts`; `RootDocument` in `routes/__root.tsx` sets `data-accent` on `<html>`, not on the page, so portalled dialogs and menus follow). `lib/accent-roles.ts` builds the primary family (primary, container, `inverse-primary`, secondary container, and the MUI `--mui-palette-primary-*` variables with their channels) from the accent's hue at fixed tones, so contrast is the same for every hue (`accent-roles.test.ts` checks it for all eight, both schemes); `theme.ts` emits them as `:root[data-accent=…]` rules (dark after light, and a system-dark one). Slate has little chroma and stays grey. Pages outside the nav keep the sky blue; error, status and chart colours and the navy brand button never change. Not built: a colour spring between pages (the variables would have to be registered with `@property`). **Dialogs and sheets are white (`surface-container-low`) like the cards; their fields stand out by the `outline` border.** **Slow loads (500ms+) on the dashboard, Trends, Compare and Net worth show `PageSkeleton`** (a route's `pendingComponent`; a search change that loads slowly shows it too, quick ones never do). Count badges (Pending on the nav, unread on the bell) are tertiary, not error. Titles take their role's weight (500); 600 and up is for data and the current item. Stat tiles: green and red ones carry meaning, the headline is `tone="primary"`, the rest `neutral`. **Form dialogs wider than `xs` are full screen on phones** (`FormDialog` sets `fullScreen` under 600px; the theme's `paperFullScreen` undoes the card margin, corners and height cap); the `xs` ones stay cards. The sheet slides on MUI's plain curve, not the `linear()` spring, which Safari animates badly.
- **PWA** (installable, with a small service worker; `public/site.webmanifest`, `public/sw.js`, `public/offline.html`, `lib/pwa.ts`, `components/pwa/PwaRegister.tsx` and `InstallCard.tsx`). The manifest (`id`/`scope` `/`, `display: standalone`, plain and **maskable** icons from `public/icon-*.png`, shortcuts to Transactions, Month plan and Accounts) plus the iOS tags and `viewport-fit=cover` in `routes/__root.tsx` make it installable on Android, desktop and iPhone (Share, Add to Home Screen). **The service worker keeps only the app's own static files and never a page, an API answer or a server-function response** (they hold money data and depend on the sign-in, so they always come from the network: nothing private is left in a cache and nothing can show stale figures): built files under `/assets/` are cache-first (their names carry a hash), `/docs/` images and the icons are stale-while-revalidate, the cache is capped at 150 entries, and a page that cannot be reached shows `/offline.html` (a static page with no data). **Offline reading of data is deliberately not built**; it would be a separate decision (what to keep, for whom, how to wipe it on sign-out). A new version **waits until the person taps Reload** (`PwaRegister` shows a snackbar and sends `SKIP_WAITING`, then reloads once on `controllerchange`), so the app never changes mid-entry; a running app checks hourly and when it returns to the foreground. **It registers only in a production build** (`import.meta.env.PROD`), so `just dev` is never served stale files. `startPwa` (called from the root) captures the browser's one-time `beforeinstallprompt` early and `useInstall` (an external store) hands it to the Settings **Install the app** card, which also covers the standalone case and the iOS instructions. The manifest is served by the static handler as `application/octet-stream`, which browsers accept; a route serving it as `application/manifest+json` is the tidy-up if a browser ever objects. **`theme-color` is one tag**: the head merges meta tags by name, so a light and a dark one would leave only the last. Tests: `lib/pwa-manifest.test.ts` (manifest fields and files, the worker's rules) and the `pwa` e2e spec (manifest, registration and activation, nothing private kept, the Settings card). Not built: offline data, push notifications, background sync, a custom install banner outside Settings.
- Dashboard (`/dashboard`, the home page) and charts: the charts are hand-drawn, not a library (`components/charts/`): SVG only for lines and washes with non-scaling strokes, everything with text (axis labels, dots, tooltips) in HTML on top. They follow the dataviz rules: 2px lines, bars at most 24px with a 4px rounded tip, hairline solid grid, a legend for two or more series, a hover/focus readout, and a "show as a table" toggle on every chart card. Chart colours are `--chart-income`, `--chart-expense` and `--chart-line` (`CHART_LIGHT` / `CHART_DARK` in `lib/m3.ts`), validated with the palette checker; dark mode has its own steps. Income and expense are green and orange, not red, because red/green fail for deutan colour vision. Net worth comes from `GET /stats/balance-trend` (computed from transactions on demand, each account at its current manual rate); income/expense per month from `GET /stats/monthly`.

- Account pickers: `components/transaction-form/AccountPicker.tsx` is a type-to-search `Autocomplete` (matches name, group, currency, bank, number) and each option shows the account's balance on the right (`AccountChoice` = `AccountRef` plus an optional `balance`; an archived account kept for editing has none). Account, From and To in the transaction form, "Pay from" in the subscription form, and the import upload and assign-transfer pickers all use it (the old `accountMenuItems` is gone). The dialog is `fullWidth` at the default `sm` width (`FormDialog`'s `fullWidth` prop). The balance is small and secondary, pushed to the right of the option.
