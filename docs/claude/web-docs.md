# In-app guides (Docs) and the Android copy

- **Docs** (`/docs` and `/docs/$slug`, `routes/_protected/docs.index.tsx` and `docs.$slug.tsx`, sidebar group Help, icon `article`) is the in-app guide to what each feature is and how to use it. **A guide is data, not a page**: `lib/docs/<name>.ts` exports a `Doc` (`slug`, `title`, `summary`, `symbol`, `accent`, `where` links and `blocks`), `lib/docs/index.ts` lists it in `DOCS`, and the index and article pages draw it. Blocks are `h2` (with an `id`, which feeds the "On this page" list), `p`, `steps` (numbered), `list`, `callout` (tip, note or warning), `example` (a worked table) and `faq`; text may use `**bold**` for the name of something on screen and `[label](/page)` for a link that stays inside the app (`inlineSegments`; `DocBlocks` renders it with `RouterLink`, and **a test fails when a link points at a page that does not exist**, `pageExists`: every sidebar destination, `/settings`, `/profile`, `/notifications` and the guides themselves), and nothing else. **Link the first mention of a page in each section** so the guides are easy to move around in. `DocBlocks` is the one renderer, so every guide looks the same. A test checks every guide: unique slugs, unique heading ids, balanced `**`, links to real pages, and unique block and item text (it is the React key, since react-doctor bans index keys). **To add a guide**: write the file, import it into `DOCS`, and keep it in step with the feature (a guide that is wrong is worse than none). Guides so far, in the index order (setting up, organising, bills, planning, then reports and the rest): Accounts, cards and groups; An account's page; Import a bank statement; Refunds, transfers and corrections; Categories; Tags; Groups; Subscriptions and recurring bills; Bills that change each month; Budget and spending limits; Savings goals; Month plan and available to spend; Split your salary; Reports (Compare, Trends, Net worth, needs and wants); Places and the map; Backups and restoring. Not yet written: Vendors, Templates, Trash, and a guide for Settings' security cards (two-factor, sessions, password). Each file names the CLAUDE.md paragraphs it must stay in step with. **Search** (`searchDocs` in `lib/docs/search.ts`, the box on the Docs page, `?q=` in the URL): a guide matches when it contains every word typed, in any order, ignoring case and the `**`/link markup, across its title, summary and every block; title matches rank first, then the summary, then how often the body mentions the words; a match found only in the body shows its section and a passage, and the card opens the guide at that section (`#id`). **Screenshots** are an `image` block (`src` = `/docs/<name>.webp`, `alt`, real `width` and `height` so the page does not jump, optional `caption`; `Shot` in `DocBlocks` draws it lazy and outlined) and live in `apps/web/public/docs/`, which the build copies into the image. **They are made, not hand-captured**: `just docs-shots` (`e2e/docs-shots.spec.ts`, which `playwright.config.ts` leaves out of every other run through `DOCS_SHOTS`) seeds a user (`shots@example.com`, the seed's made-up data, `app.seed --email`) in the e2e database, adds a credit card with a statement through the API, signs in, and for each screen clips the page's content (not the sidebar, and below the banner, `BANNER`) to at most 900 px tall, adds `PAD` (28 px) of the page's own background all round so rounded corners are not cut off (a shot cut at the maximum height also fades out at the bottom), and saves a **WebP converted by Chromium's own canvas** (no image library installed), printing each file's size so the `width`/`height` of its block can be copied; they come to 18 to 50 KB each. **Light mode only.** One so far (`compare` in Reports, a whole page that depends on loader data); to add one, add a `shoot(...)` to the spec, run `just docs-shots`, and put an image block in the guide. A test checks every block's file exists, is a `.webp` under 150 KB, has a real alt, and is used once; the search reads alt and caption. Re-shoot only when a screen a guide shows has really changed, since each new version stays in git history. **Live examples** are the alternative to a screenshot for a self-contained piece of the app: a `demo` block (`id`, `title`, optional `caption`) draws the **real component** with made-up data from `lib/docs/demo-data.ts`, so it can never go stale, follows dark mode and the theme, reflows on a phone and is real text. It sits in a dashed frame labelled "Example with made-up data", inside an `inert` box with `pointer-events: none`, so nothing in it can be focused or pressed and it sends nothing. An id lives in `lib/docs/demo-ids.ts` (`DEMO_IDS`) and its component in `components/docs/Demos.tsx` (a `Record<DemoId, ...>`, so the type requires both); the component must be presentational (props only, no loader, server function or app shell). Four so far, all replacing screenshots: `card-statement` (`CardStatementPanel`, Accounts guide), `plan-agenda` (`PlanAgenda` fed by `planDays(planDemo)` in the card the page draws it in, Month plan guide), `budget-limits` (`BudgetSummary` and four `BudgetLineCard`s, Budget guide) and `salary-rules` (the whole `SalaryRulesCard`, whose dialogs only mount when opened, Salary guide). The fixtures are typed against the generated API types, so a schema change breaks them at compile time instead of leaving a stale example. Prefer a demo for a piece built from props and a screenshot only for a whole page. **Each page has one "Guides" link** (`GuideLinks` in `PageHeader`, a single pill however many guides there are, so the header never grows with the docs): it opens **`/docs?q=<term>`**, the docs index with its **search box filled in** for that page (`GUIDE_SEARCH`: "budget", "month plan", "net worth"; an account's own page uses "account"; `docsSearchFor` gives the term, none for a page without guides), so it lists every guide that has to do with the page, the mapped ones first and any other that mentions it; a test checks each term finds that page's own guides), taken from `GUIDES_FOR_PAGE` in `lib/docs/for-page.ts` (`/accounts` Accounts, cards and groups; `/accounts/<id>` An account's page through `guidesForPath`; `/transactions` Refunds, transfers and corrections; `/subscriptions` Subscriptions and Bills that change; `/budget` Budget and Savings goals; `/plan` Month plan; `/pending` Split your salary; `/import`; `/compare`, `/trends` and `/net-worth` Reports; `/categories`, `/tags`, `/groups` and `/places` their own; `/settings` Split your salary and Backups and restoring). It needs no change to a page: add a route to the map, and a test checks every key is a real page and every slug a real guide. A page with no entry (vendors, tags, settings...) shows none, and the guides themselves never do. `docs-shots` finds a page's header by its `data-page-header` attribute (not a fixed height), so a header that grows a row does not spoil a shot. Not built: dark-mode screenshots, guides for Vendors, Templates, Trash and Settings' security cards, a link from each Settings card to its guide.
- **The Android app's guides are generated from the web's** (`apps/web/src/lib/docs/export.ts`, `export.test.ts`, `apps/android/app/src/main/assets/docs.json`, `just docs-json`, `just check-docs-json`). The app bundles the guides instead of fetching them (the API has no docs; the web is the one source), so it reads them offline. `exportDocs` keeps the text blocks (h2, p, steps, list, callout, example, faq) with their `**bold**` and `[label](/page)` markup and leaves out what is made of web components (`demo` and `image` blocks), naming each in the guide's `extras` so the app can say the web version has more; `WEB_ONLY` (only `import` so far) marks a guide about something the app deliberately does not do, and the app says so at the top of it. **After changing a guide run `just docs-json` and commit the file**: `export.test.ts` compares it byte for byte with what the guides produce, so `just test-web` and the CI web job (a `just check-docs-json` step, with the fix named in its message) fail when it is stale; `WRITE_DOCS_JSON=1` makes the same test write the file. On Android `DocsLogic.kt` reads it (`parseDocs`), ports the web's search (`searchDocs`, tested against the real file: every link must resolve) and maps links to screens (`docLink`: a guide, a tab or screen, or the web), and `DocsScreen.kt` draws it with native components.
- **The iOS app reads the same file**: `apps/ios/project.yml` adds `apps/android/app/src/main/assets/docs.json` to the app's resources from where it is generated, so there is one copy and `just docs-json` updates both apps. `DocLibrary.bundled` decodes it; `DocBlock` knows the text blocks and decodes any other kind as `.other`, which is not drawn (`DocsTests` fails if a guide has one, and checks that every guide link resolves, against the real file). `DocText` turns the markup into an `AttributedString` with the system's Markdown (inline only): a link to `/docs/<slug>` opens that guide in the app (the `maalu-guide:` scheme, caught by `openURL` in `DocView`), a link to any other page shows as bold words. `DocSearch` ports `searchDocs` (and `excerpt`), so a search finds the same guides in the same order and opens a body match at its section. A guide's `extras` are named in an "On the web" note, and `webOnly` adds one at the top. Guides live in More > Guides (`DocsView`).
