# End-to-end tests

End-to-end tests (`apps/web/e2e`, `playwright.config.ts`, Playwright; `just e2e`, CI job `e2e`): a real Chromium against a real API on Postgres and a **production build** of the web app, started by Playwright itself on ports 8101 and 3101 with their own database `maalu_e2e` (`just e2e` creates it, CI's Postgres service is it), so `just dev` and its data are never touched. **Each test signs up its own user** (`signUp` in `e2e/helpers.ts`, email `e2e-…@example.com`: the API refuses `.test` as reserved) and sets data up through the API with `apiAs` (accounts, transactions) instead of clicking, so tests are independent and run in parallel (half the cores as workers locally (at most 4, because one API and one web server serve them all and more only time out) and 2 in CI, `E2E_WORKERS` to change it (a number or a percentage), and `just e2e` runs at the lowest CPU priority so the machine stays usable: one API and one web server serve all of them; the web server's stderr is hidden because tests closing pages make it log harmless "Error: aborted" / ECONNRESET traces, `E2E_VERBOSE=1` shows it). `open(page, path)` waits until React has taken over the page (`hydrated`: elements carrying `__reactProps$…`) before a form is used, because a form submitted early goes the plain-HTML way and reloads the page empty (a sign-up that ends on `/register?email=…`); "no network traffic" is not enough, since hydration can still be running on a slow or busy machine. Any new spec that clicks right after a page load must open it with `open()` (or call `hydrated(page)`), never `goto` plus a fixed wait. Locators go by role and label (never CSS classes) so restyling does not break them. The `two-factor` spec turns two-factor on through Settings using real codes: `totp(secret, steps)` in `e2e/helpers.ts` makes the 6-digit code an authenticator app would show for the key the setup dialog displays (RFC 6238, SHA-1, 30-second steps). **The API accepts one step either side of its own and each step once**, so the second code in a test comes from `steps = 1`; recovery codes (each works once) are used for everything after that. It checks that sign-in needs the code, a wrong code and a reused recovery code are refused, turning it on signs out the other devices, and turning it off needs the password and a code. The `plan`, `docs`, `pending` and `varying-bills` specs cover the month plan (where the money runs out, receiving a salary with the real amount, paying a bill), the guides (the sidebar link, links inside a guide, the On this page list, a missing guide), the Pending screen (an automatic rule moves at once and the other waits, review and edit, dismiss, the switch in Settings) and a varying dollar bill (an estimate, paid with the real amount and what it cost, an own-currency bill with no rate fields). The `cards` spec adds a debit card on an account's page and picks it on a purchase (the account and the Debit card method follow, the row names the card, the balance drops), filters Transactions to one card (from the Filters drawer), spends on a credit card (owed on its own account, the bank untouched) and pays it off with Repay, and checks the account form explains each group and no longer offers Debit Card. The `account-detail`, `kinds-reports` and `salary-prompts` specs cover an account's page (the list's link, only its own rows, a transfer read from each side, search, Add transaction starting in it, a missing account, the balance chart and its range, the running balance), needs and wants in Compare and Trends, the split-waiting notification leading to Pending, and the split offered after a planned salary is marked received (with what really arrived, and not when there are no rules). The `category-spend` spec checks the Categories page: a category's spending for the month (a parent including its sub-categories, a dash for none, the header pill), the Limit donut on a category a limit covers and on its sub-category, a red one close to its level, the figure leading to that month's transactions, and an empty previous month. The `bank-chips` spec checks an account's bank shows as a chip beside its name with a logo for MIB and BML (and the filter chips), none for another bank, and the line under the name keeping just the number. The `spending-trend` spec checks the dashboard's Spending by month card: six categories over two months give a chip for each of the four biggest plus Other (the two smallest folded in, with their sum), pressing a chip follows it (pressed, its name in the subtitle) and again lets go, and the 12-month switch changes the span and lets go of a followed category. The `adjustment-category` spec checks a balance adjustment appears in the transaction list as "Balance adjustment" while the Categories page has no category for it (nothing to sort). The `backup` spec downloads a real backup from Settings and restores it into a second person's browser context (`newPerson`), comparing balances and totals through the API, and checks the refusals (data already there, a damaged or foreign file). The `pages` spec opens every page and fails on the "Something went wrong" screen, so a loader broken by an API change is caught. The web server reaches the API at `127.0.0.1`, not `localhost`. Add a test for each new flow a person clicks through; unit and API tests stay the place for rules. Chromium is a one-time download (`just e2e-install`, about 150 MB).
