# Sign-in and security (API and its web side)

- **Registration is controlled by `REGISTRATION`** (`Settings.registration`, `UserService.registration_open`): `auto` (default) lets an account be created only while none exists, so the first person to open a new instance is its owner and sign-up then closes; `open` lets anyone; `closed` lets no one (accounts come from `just seed` or the database). `POST /auth/register` answers 403 "Registration is closed" and `GET /auth/registration` (`{open}`, no login) is what the web login page (hides "Create one") and register page (shows a closed notice) read. Existing accounts sign in as usual. Maalu is self-hosted only, so the default is closed-after-owner. A way for the owner to add a partner is planned, not built. Tests default to `open` in `conftest.py`; `test_registration.py` covers the modes.
- **Passwords.** `POST /auth/password {current_password, new_password, code?}` (`UserService.change_password`) needs the current password and, when two-factor is on, a code or recovery code (a stolen session plus a known password must not be able to lock the owner out). New passwords follow the sign-up rules (8 to 128 characters) and must differ from the current one. It keeps this session and **ends the others**. A wrong current password is **422, never 401**, and counts toward the **sign-in rate limit** for that account (`rate_limit.login_failed`), so a stolen session cannot be used to guess the password; the password is checked before the code. Someone who forgot theirs is recovered by the operator, with no email: `just reset-password EMAIL` (`python -m app.admin reset-password EMAIL`, in Docker `docker compose -f docker-compose.prod.yml exec -it api python -m app.admin reset-password EMAIL`) asks for the new password twice, hidden, sets it (`UserService.set_password`), signs the account out everywhere (`SessionService.end_all`) and leaves two-factor as it is. Tests reach the database through `client.session_factory`.
- **Sessions are rows, and ending one deletes the row** (`models/session.py`, `services/session.py`, table `sessions`). Signing in makes a random 256-bit token (`security.new_session_token`); only its SHA-256 hash is stored, so a copy of the database holds nothing that signs in. The token is the bearer token (there is no access JWT any more; the only JWT left is the five-minute two-factor challenge). `get_current_user` / `CurrentSession` (`dependencies.py`) look the token up on every request, which is one small query. A session lasts `session_days` (30, `SESSION_DAYS`) **after its last use**: using it pushes the end out again, at most once an hour (`TOUCH_EVERY`), so a device you use now and then stays signed in and a lost one expires. A user switched off (`is_active`) fails the lookup. Expired rows are removed at the user's next sign-in. Each session records the browser (`User-Agent`, 255 characters) and the address it signed in from, only to tell your devices apart. Routes: `POST /auth/logout` (ends this session at once), `GET /auth/sessions` (yours, most recently used first, `current` marks the asker), `DELETE /auth/sessions/{id}` (404 for someone else's), `POST /auth/sessions/end-others` (declared before the `{id}` route). **Turning two-factor on or off, or making new recovery codes, ends your other sessions** (they were made without the second factor); a failed attempt ends nothing. Tests move time through `services.session._now`.
- **API keys** (`app/api_scopes.py`, `models/api_key.py`, `services/api_key.py`, `routers/api_key.py`, `schemas/api_key.py`, table `api_keys`; web `components/api-keys/*`, `lib/api-keys.ts`, `server/api-keys.ts`, the **API keys** card in Settings) let a bot, a script or an AI agent use Maalu without a password, each with exactly the permissions the person chose and an end date. **A key is `mlk_` plus 256 random bits, shown once and stored only as its SHA-256 hash** (like a session token); the list shows `prefix` (the first 12 characters) to tell keys apart. It is sent as the same bearer token as a session: `get_principal` in `dependencies.py` tells them apart by the prefix. **Permissions are scopes, `area:action`**: areas `accounts`, `transactions`, `categories`, `vendors`, `tags`, `budget`, `goals`, `subscriptions`, `plan`, `reports`, `import`, `notifications`, actions `read`, `write` (create and change) and `delete`, **each standing alone** (reading does not imply writing, writing does not imply deleting). **Roles are only named starting sets** (`viewer`, `reports`, `assistant`, `editor`, none of which can delete); **a key stores the scopes it was given, not the role's name** (`role` is a label worked out from them, "custom" when no role matches), so changing a role's definition later never widens a key that exists. **What a key can reach is decided by method and path in `api_scopes.ROUTES`, closed by default**: a route not named there is out of reach of every key; `/auth`, `/users`, `/backup`, `/email`, `/api-keys`, `/attachments` (also under a transaction), `/places`, `/salary-rules`, `/salary-split-tasks`, `/transactions/export` and a transaction's `/salary-split` are named as **never** (browser-only), reports (`/transactions/categories`, `/totals`, `/places`, `/stats`) and the plan (`/stats/available-to-spend`) are their own areas, the action comes from the method (`DELETE` and the `/purge` and `/permanent` paths are `delete`, other non-reads are `write`), and `/currencies` and `/whoami` are readable by any key. A key refused gets **403 naming the missing permission** ("This API key does not have the permission transactions:write"); an unknown, expired or deleted one gets 401. **Managing keys needs a signed-in person, never a key** (the routes depend on `CurrentSession`, which an API key can never satisfy, and the path rules refuse them too), so a key cannot make a stronger key. **Lifetime:** `expires_in_days` (1 to 3650, default 90 in the form, null = never) counted from now; it can be shortened, extended or removed later (`PATCH` with an explicit null). **Rotation** (`POST /api-keys/{id}/rotate {grace_hours}`, 0 to 168) replaces the secret and shows the new one once; with a grace period the old hash is kept in `previous_hash` and works until `previous_expires_at` (then it is 401), with none it stops at once; the name, permissions and end date are unchanged. Deleting a key stops it at once. At most 20 keys a person; each request is counted per key (300 a minute, `rate_limit.check_api_key`, 429 past it); a key in use is noted at most once a minute (`last_used_at` and the address). `GET /whoami` tells a key what it may do (and a person "session"); `GET /api-keys/scopes` is the catalogue the form draws (areas, actions, roles). **Keys are not in backups** (`api_keys` is in `EXCLUDED`: a backup file must never carry a secret that signs in) and every key goes when its user does. **Reaching the API from outside** (`routes/api.v1.$.ts`, `utils/key-proxy.ts`): the API has no published port, so the web server carries outside requests across: `https://<your maalu>/api/v1/...` is forwarded to `API_URL/api/v1/...` and the answer comes back (status, `Content-Type`, `X-Total-Count`, `Retry-After`, never cached). **Two kinds of caller use this door, and the proxy never decides what they may do (the API does: permissions, expiry, rate limits).** (1) **An API key** (`Authorization: Bearer mlk_...`), for a bot, script or AI agent. (2) **A native app** (the Android app in `apps/android`; iOS later), which is not a browser and cannot use the website's own sign-in: it signs in at `POST /api/v1/auth/login` (form-encoded, and `POST /api/v1/auth/login/2fa` for a second factor), the **only two calls that need no credential** (`isOpenRoute`, method and exact path), and then sends the **session token** it was given as `Authorization: Bearer <token>` like a browser session does through the website (`credentialFromAuthorization`: a session token is `token_urlsafe(32)`, exactly 43 URL-safe characters, and is told from a key by its shape; a key starts `mlk_`). Everything else without a credential is `401 "Sign in, or send an API key..."`, a token of the wrong shape is the same, and a well-formed one the API does not know is the API's own `401`. It still only forwards to `/api/v1/` (`upstreamPath` refuses an empty path, `..`, odd characters and over 300 characters), passes on the caller's address as `X-Forwarded-For` (so the API's `last_used_ip` and its sign-in and key limits are about the caller, not the web server: ten wrong passwords for one email or thirty from one address in fifteen minutes is a `429` here too), caps a request body at 10 MB (413) and answers 503 when the API cannot be reached. **The website's browser does not use this door**: it keeps its own server functions and encrypted cookie, so nothing about the website changes. What a session token may do through here is exactly what it may do against the API (everything a signed-in person can), unlike a key, whose routes are a closed list; ending it (`POST /auth/logout`, or "Sign out" in Settings' device list) ends it everywhere. One address and one Cloudflare tunnel serve the browser, the keys and the apps; no compose change is needed (the API stays unpublished). A native app's reachability check is `GET /health` first and, since the web address does not serve that, `GET /api/v1/whoami` (any JSON `401` means a Maalu server answered). In development the same calls work at `http://localhost:3000/api/v1` (through the proxy) or `http://localhost:8000/api/v1` (straight to the API, which is what `just dev-api` and the Android emulator use). Tests: `utils/key-proxy.test.ts` (the credential rule, the open routes and the path rule); end to end it was checked by running the web server in front of the dev API: wrong password `401`, login `200` and a 43-character token, `GET /accounts` with it `200` with `X-Total-Count`, no credential `401`, `GET /auth/login` and `POST /auth/register` `401`, a made-up token `401`, logout `204` and the same token `401` after. Not built: CORS for a browser on another origin (bots, scripts and apps do not need it), a native-only marker header (it would add nothing, anyone can send it), registration through the proxy (the app has no "Create account").
- **Sign-in alerts** (`app/services/login_alert.py`, `users.notify_login`, default **on**, `PATCH /users/me`, in backups, shown in Settings next to the email switch when email is set up). Every completed sign-in (`POST /auth/login` without two-factor, or `/auth/login/2fa` after the code; **not** a wrong password, not the first step of a two-factor sign-in, not an API key) emails the sign-in address one short message: the device (`describe_device`, the same reading as the web's `lib/user-agent.ts`; the app's own `Maalu-Android` agent reads "Maalu app on Android"), the address and the time in UTC, plus "if it was not you, change your password and sign out your other devices" with a link to `/settings` when `APP_URL` is set. It is independent of `notify_email` (a security alert, not a digest) and needs only SMTP (`mailer.configured()`); with none, nothing happens. **It is a FastAPI `BackgroundTask` queued by `_start_session`**, so it runs after the answer and a slow or broken mail server can never delay or fail a sign-in (`login_alert.send` swallows and logs `MailError`); it is given plain values (email, User-Agent, address), never the request's database session. Nothing about the address is looked up (no geolocation call). Not built: a "new device only" mode, an alert for a failed sign-in, and a push notification to the person's other devices.
- **Rate limiting** (`app/rate_limit.py`, `Settings.rate_limit` / `RATE_LIMIT`, on by default) slows down guessing, in memory: a sliding window per key, nothing to install, a restart forgets it (it assumes one API process, the default; with several workers each counts on its own). Failed password attempts count per **account** (the email trimmed and lower-cased, whether or not it exists, so the answer never shows which emails are registered) and per **client address**: ten wrong passwords for one email, or thirty from one address, in fifteen minutes answer **429** with `Retry-After` and "Too many attempts. Try again in N minutes" (a `RateLimitedError` turned into the response by a handler in `main.py`, so services stay free of FastAPI). A right password clears that account's count. Wrong 2FA codes also count per address (twenty), on top of the per-user lock; sign-up attempts per address (ten an hour). **The browser never talks to the API, so the API only sees the web server**: `apiRequest` passes the visitor's address in `X-Forwarded-For` and uvicorn replaces `request.client` with it only for hosts in `FORWARDED_ALLOW_IPS`, which `docker-compose.prod.yml` sets to `*` because the API has no published port. Without that every visitor would share one limit. Behind a reverse proxy the web server needs the proxy to set `X-Forwarded-For`; if the web port is exposed directly a client can forge it, which only defeats the per-address limit, not the per-account one. A locked account locks the owner out of signing in for the rest of the window too (the price of a per-account limit). Tests turn it off (`RATE_LIMIT=false` in `conftest.py`) and `test_rate_limit.py` turns it on with a fake clock.
- **Two-factor sign-in** (authenticator-app codes, TOTP) is built in the API, not with a library service: `app/two_factor.py` (pure helpers: pyotp codes, Fernet encryption of the secret with a key derived from `SECRET_KEY`, recovery codes, the QR as an SVG data URI), `UserService` (state and rules), `routers/auth.py`. Columns on `users` (`two_factor_secret` encrypted, `two_factor_enabled`, `two_factor_last_step`, `two_factor_failures`, `two_factor_locked_until`) and a `recovery_codes` table (only SHA-256 hashes; `used_at`). Setup is `POST /auth/2fa/setup` (a secret, nothing changes yet; asking again before it is confirmed returns the **same** secret, so a repeated or racing request can never leave the screen and the server holding different ones) then `/auth/2fa/enable {code}`, which turns it on and returns ten recovery codes **once**; `/auth/2fa/disable` and `/auth/2fa/recovery-codes` need the password **and** a code. Sign-in becomes two steps: `POST /auth/login` returns `{two_factor_required, challenge_token}` and no `access_token` (a challenge is a five-minute JWT with a `scope` claim that `decode_access_token` refuses); `POST /auth/login/2fa {challenge_token, code}` gives the token. A code is accepted a step either side of now, **once** (`two_factor_last_step`); a recovery code works once; five wrong codes in a row lock the second factor for five minutes (`check_second_factor` commits the count before raising, since the failing request would roll it back). A wrong password or code on a signed-in route is **422, never 401**: the web app takes a 401 to mean the session ended. Changing `SECRET_KEY` makes stored secrets unreadable, so two-factor has to be set up again (it already signs everyone out). Someone who lost both the app and the codes is recovered by the operator: `just disable-2fa EMAIL` (`python -m app.admin disable-2fa EMAIL`, in Docker `docker compose -f docker-compose.prod.yml exec api python -m app.admin disable-2fa EMAIL`). Tests freeze the clock through `two_factor._now`. iOS: the login screen's second step (`TwoFactorCodeSection`, `LoginModel`) takes the authenticator code (number pad, one-time-code autofill) or, after "Use a recovery code instead", a recovery code; "Back to sign in" keeps the email, and a 401 "Sign in again" (the challenge ran out) goes back to the password saying the sign-in timed out, while a wrong code stays on the code. Setting it up and managing it are not on iOS yet.
- **iOS Settings > Security** (`Features/Settings/`): *Change password* (`ChangePasswordView`, `PasswordDraft`: eight characters, typed twice, a code field only when `two_factor_enabled`; `POST /auth/password`) and *Where you are signed in* (`SessionsView`, `SessionsModel`: swipe to end one, a confirmed "Sign out all other devices"; `DeviceName` names a user agent like the web's `describeDevice`, and the app's own `Maalu-iOS/0.1` reads "Maalu app on iOS"). Two-factor setup is not on iOS yet.
