# Platform (API and its web side)

- **Balance snapshots** (`models/balance_snapshot.py`, `services/snapshot.py`) are what each account held and was worth at the end of each **completed day** (`balance`, `exchange_rate`, `base_value`, one row per account per day; today is never stored, it is worked out live). `GET /stats/balance-trend` reads them for past days and computes only today and later from transactions (`StatsService._snapshot_points` / `_live_points`), so the chart no longer replays history and **revaluing an account never rewrites the past** (each day keeps the rate it had). Balances stay derived from transactions and are the source of truth, so snapshots are **repaired when an older transaction changes**: an `after_flush` listener on every `Session` (`mark_stale_snapshots`) writes a row in `balance_snapshot_dirty` (account, earliest affected day; upserted, keeping the earliest) for any added, changed, trashed or deleted transaction dated before today, for an account that is new (marked from 1900 to build its history), or whose opening amount changed. Today and later are never marked. `SnapshotService.repair(user_id=None)` first rebuilds each marked account from its mark (`rebuild`: replaces the rows from that day, keeping the rate of any day that already had one), then adds the days since each account's last snapshot; the trend calls it for the user before reading, and the daily `snapshot_balances` job (00:10 UTC) calls it for everyone, so the chart is right even with no worker running and the job mainly keeps the day's rate honest. A day before an account's first snapshot counts its opening amount at the current rate; archived accounts keep their snapshots but stay out of the trend. Days go by UTC (`snapshot._today()`, which tests replace with a fake clock; `stats.py` reads it as `snapshots._today()` so the patch reaches it). The migration marks every existing account stale, so history is built on first read. If the exchange rate is edited before the job has snapshotted yesterday, yesterday takes the new rate (a known one-day edge).
- **Background jobs** run in a separate worker process with procrastinate (`app/jobs.py`; the queue is Postgres tables, so nothing else to install): `just dev-worker` locally, the `worker` service in `docker-compose.prod.yml` (the API image with the command `procrastinate --app=app.jobs.app worker`; run one) in production. The API never runs a job. A job is an `@app.task` function that opens its own `SessionLocal` session (there is no request); `@app.periodic(cron=...)` above it schedules it, and procrastinate defers a periodic job once however many workers run. Jobs so far: `purge_expired_sessions`, daily at 03:17 (`SessionService.purge_expired`), `snapshot_balances`, daily at 00:10 (see Balance snapshots), `plan_subscriptions`, daily at 00:20 (see Subscriptions plan their next payment), and `purge_orphan_attachments`, daily at 04:30 (see Attachments), `generate_notifications`, daily at 04:00 (see Notifications), `refresh_exchange_rates`, daily at 16:30 (see Rate refresh), and `email_notifications`, every ten minutes (see Notifications: Email). The queue's schema is an Alembic revision (`b4e8d1a7c3f2`) that runs a **frozen copy** of procrastinate's SQL (`migrations/sql/procrastinate_3_10_schema.sql`) through asyncpg's simple-query `execute` (asyncpg refuses several statements in one prepared statement), and `include_object` in `migrations/env.py` keeps `procrastinate_*` tables out of autogenerate. **When procrastinate is upgraded, add a revision that runs its new files from `procrastinate/sql/migrations/`**, do not edit the frozen one. The worker needs `PYTHONPATH` to include `apps/api` (the compose service and `just dev-worker` set it). Tests call the job's plain function with `client.session_factory` and use procrastinate's `InMemoryConnector` to check a task can be deferred; they never need a worker or Postgres.
- **Backup and restore** (`services/backup.py`, `routers/backup.py`, Settings > Backup) is one JSON file of everything the user owns. `GET /backup` downloads it; `POST /backup/restore` takes the file as the request body (not multipart; capped at 200MB, held in memory). It is **metadata-driven**: `OWNED` (tables with `user_id`) and `CHILDREN` (tables tied to an owned row through one column) name the tables, and rows are read and written straight from the database tables, so a new column is backed up automatically. **A test fails when a new table is in neither `OWNED`/`CHILDREN` nor `EXCLUDED`**, forcing a decision (excluded: users, sessions, recovery codes, the exchange-rate cache, balance snapshots, which are rebuilt, and attachments, whose files live in storage). The file has `format`, `version`, `settings` (base currency, start-from-template, default account), `counts`, a SHA-256 `checksum` of the tables and the `tables`. **A restore goes only into an empty account** (409 otherwise; "empty" means no row in any included table, **except the budget row itself**: it is only settings, made by looking at the budget page (so every new account has one after its first visit to the dashboard), and a restore deletes it and puts the backup's own in; a budget with limits is not empty because `budget_lines` is counted), gives **every row a new id** (so the same file can go into two accounts, or back into the instance it came from, without colliding; foreign keys are rewritten through id maps, and columns that point into the same table, like `refund_of_id` and `parent_id`, are filled after the rows exist), sets the user's base currency and settings from the file, and marks every restored account stale so its snapshots are rebuilt on first read. Tables go in dependency order (`sort_tables`) in chunks of 1000. Any problem (not our format, other version, bad checksum, unknown table or column, a link to a row that is not in the file, a database error) is a 422 and **nothing is restored**, because the request's transaction rolls back. The backup holds no password, session or two-factor secret but is the user's financial data in plain text. The web side forwards both through `routes/api.backup.ts` (the browser cannot reach the API) and, after a restore, re-reads `/users/me` to refresh the base currency the session cookie caches; `BackupCard` is the Settings card.
- **Notifications** (`models/notification.py`, `services/notification.py`, `routers/notification.py`, table `notifications`) are things in your data worth a look, found by `NotificationService.sync` and kept as rows you can read and dismiss. Three kinds, each with a switch on the user (`notify_payments`, `notify_budget`, `notify_goals`, all default on, set with `PATCH /users/me`, in backups): **payments** (a planned transaction, live, dated within `DUE_SOON_DAYS` (3) ahead or already past: `payment_due`, and later a separate `payment_overdue`), **budget** (a line of the *current* period that is `warning` or `over`, one per line, period and status) and **goals** (`goal_reached`, once). **It is derived, never entered**: every event has a `dedupe_key` (`due:<transaction id>`, `overdue:<id>`, `budget:<line id>:<period start>:<status>`, `goal:<id>`), unique per user, and `_add` makes one only if the key is unseen (a parallel look that loses the race is refused by the unique constraint inside a savepoint and ignored), so looking again never repeats. **Dismissing keeps the row** (`dismissed_at`, hidden from lists and counts) so a dismissed event is not announced again; reading sets `read_at`; `purge_old` sweeps anything older than 90 days. It is looked for by the daily `generate_notifications` job (04:00 UTC, which also sweeps) **and on read** for one user (`GET /notifications`, `/notifications/unread-count`), throttled to once per `SYNC_EVERY_SECONDS` (5 minutes) per process (`_last_sync`; tests set it to 0), so the bell is right with no worker running. **The time is noted when a look finishes, not when it starts**: the bell's count and the list load in parallel, and noting it first made the second skip the look and read before the first committed (a count of 1 over an empty list, found by an end-to-end test); two looks at once are safe because the unique key makes the second wait and make nothing twice. **Writing a transaction (create, update, trash) and making a salary task clear the user's throttle** (`notification._last_sync.pop`), so news that comes from your own change (a bill that makes the money run short) shows at the next read, not up to five minutes later. Routes: `GET /notifications` (`unread=true`, paged, `X-Total-Count`), `GET /notifications/unread-count`, `POST /notifications/read-all` (declared before `{id}`), `POST /notifications/{id}/read`, `DELETE /notifications/{id}` (dismiss). **Notifications are not in backups** (`notifications` is in `EXCLUDED`: they are worked out again). Web: the bell in the top bar (`NotificationBell`, badge from the `_protected` layout's loader through `unreadCountFn`, so it refreshes after every action and on tab focus; a popover with the newest eight, clicking one marks it read and opens its `link`), the Notifications page (`routes/_protected/notifications.tsx`, reached from the bell's "View all", not in the nav) and `NotificationSettings` (the three switches) on the Settings page. The type is `AppNotification`, because `Notification` is the browser's own. **Email** (`app/mailer.py`, `services/email_digest.py`, `routers/email.py`, `users.notify_email` default off, `notifications.emailed_at`): any SMTP provider through the standard library (no new dependency), configured by `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURITY` (`starttls`, `ssl` or `none`), `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM` (a sender the provider has verified), `SMTP_FROM_NAME` and `APP_URL` (so a mail can link to a page); Brevo is the documented one (`smtp-relay.brevo.com`, 587, starttls, the SMTP login and key). **Email is on only when `SMTP_HOST` and `SMTP_FROM` are set** (`mailer.configured()`); otherwise nothing is sent and Settings says so instead of showing the switch. The worker's `email_notifications` job (every ten minutes) calls `send_digests`: for each active user with `notify_email` it sends **one digest** of their notifications that are unread, not dismissed, not yet emailed and created in the last two days (`WINDOW`, so switching it on does not send a backlog; at most 20 per digest), to the **sign-in address only**, and marks them `emailed_at`; a failed send leaves them for the next run. Notification text is HTML-escaped in the mail. `GET /email/status` (`{configured, sender}`) and `POST /email/test` (a message to your own address; the provider's error comes back as a 503 reason) back the Settings card (`NotificationSettings`: a switch "Email me at …" and "Send a test email"). The flag is in backups; `emailed_at` is not (notifications are not backed up). The API and the worker both need the SMTP settings (the compose file passes them to both). Tests swap the sender with `mailer.set_sender`, so nothing connects. Not built: per-kind email switches, an immediate email (the delay is the job's ten minutes), a plain unsubscribe link (the switch in Settings is the way), password-reset mail (recovery stays the operator's command). A new kind needs a generator in the service, a `kind` in `schemas/notification.py` and `KIND_META`, and (if it should be switchable) a flag on the user.
- **The seed** (`app/seed.py`, `just seed [--seed N] [--email x@y.z]`, tested in `tests/test_seed.py`) builds **a realistic first month**, not random volume: a 10,000 MVR salary on the 1st of last month and of this month (so the dashboard's calendar month is never empty), split by two automatic rules (1,000 to MIB Savings, which the Emergency fund goal follows, 500 to BML Savings) through `SalarySplitService.on_posted`; six accounts (BML Current, Savings and USD, MIB Current and Savings, Cash) with openings as of last month's start; nine monthly bills as subscriptions with a due day (rent, broadband, mobile, electricity and water and a dollar VPS that vary, health insurance, Netflix, iCloud+), each paid when due and the next one planned by `SubscriptionService.sync`; moves between accounts (spending money, cash, a cross-currency USD top-up); groceries, meals and taxis on fixed days of the month with random amounts and times, a few one-offs (books, half returned as a refund, pharmacy, cinema, a gift card); a budget of four limits, three goals (two follow accounts, one by hand with a monthly set-aside), two templates and the next salary as a planned income. Dates are calendar-based, so a date still to come in the current month is skipped (`day()`), and `sync` plans against the real date, so tests pass `today=date.today()`. Tests use the demo user to check balances never go below zero, one planned payment per bill and two splits. Not seeded: groups, tags, attachments, imports, cards or loans.
- **Settings** are columns on `users`, changed with `PATCH /users/me` (only the fields sent change). `start_from_template` (default true) is whether the transaction form offers saved templates; it only hides the picker, templates and "Save as template" stay. The web has a Settings page (`/settings`, in the account menu) for these; the default account is still on Profile.
- **Short numbers** (`users.compact_numbers`, default off; `PATCH /users/me`; in backups; web `lib/format.ts`, `components/NumbersCard.tsx`, Settings > Numbers). How big amounts are written. **`formatMoney` is the one function every amount goes through**, and it consults a page-wide preference (`setShortNumbers`, set once per render by the signed-in layout `routes/_protected.tsx` from `user.compact_numbers`, which the **session cookie caches** like the base currency: `finishSession`, the backup restore route and `updateMeFn` keep it in step). **Off:** amounts are in full ("MVR 1,234.50"); only a tight place that asks for it (`formatMoneyCompact`: the phone strips and docks and the "Net" / "per month" pills) shortens, **from 10,000 up** ("MVR 513.58M", `COMPACT_FROM`). **On:** every amount of **a thousand and over** is shortened everywhere ("MVR 1.23K", `COMPACT_FROM_EVERYWHERE`), the tight places too. Below the threshold the full figure stays, cents and all. The short form is Intl's compact notation with two decimals (`K`, `M`, `B`, `T`), and the chart axes use `compact` in `lib/charts.ts` (K, M, B, T) whatever the setting. **The exact amount is a hover or a tap away wherever a short form is shown**: `components/Money.tsx` renders an amount (`<Money amount currency />`, `compact` for a tight place) as plain text when it is shown in full, and as a tooltip target (`FullAmountTip`: hover on a mouse, a tap on a phone with no long-press wait, keyboard-focusable, the exact figure from `formatMoneyFull`, which never shortens) when it is shortened, so a figure in full has nothing around it and nothing changes where nothing is shortened. About eighty places that print an amount as JSX text use it (the transaction rows, balances, tiles, cards); an amount built into a string (a template literal, a prop passed to a component as text) still shows its short form without the popover, and is the next thing to convert if one matters. Display only: amounts stay decimal strings everywhere else, and no input ever shows a short form. The preference is module state, which is fine for one person's page; with several people on one server the server render could briefly use the neighbour's setting, a cosmetic risk worth knowing if households are built. iOS: the switch is in More > Numbers (`ShortNumbersSection`, `PATCH /users/me`); the device keeps a copy in `UserDefaults` (`MoneyFormat.shortKey`), taken from `GET /users/me` on every sign-in or launch, so `MoneyFormat.string` shortens from a thousand up (the platform's compact notation, up to two decimals) and `MoneyText` shows a short amount as a button whose popover has the exact one (and VoiceOver reads the exact one); an amount built into a sentence is short with no popover, as on the web. **`just seed --scale N`** multiplies every amount of a seeded user (`seed.scale_money`; rates and percent rules untouched; the balance history is dropped to be rebuilt), to try millions and billions: `just seed --email big@maalu.dev --scale 100000`.
